# Method Engineering

> 建立并持续演化一种可靠的方法工程能力，首要目的始终是解决真实、具体且有边界的方法工程问题。

本项目的现行愿景见 [`docs/vision/charter.md`](docs/vision/charter.md)。

## 方法工程的含义

面对具体、有边界的问题，利用已有可靠知识、必要的研究与实际验证，系统地构造、选择、裁剪、评价和改进解决问题的方法。

我们优先继承成熟知识与方法，只在真实问题或实践证据暴露出不足时研究、修改或增加新的结构。框架、术语和结构的演进服务于解题，而不是取代解题。

## 方向级边界

- 从真实问题、Case、执行记录和失败经验获得反馈。
- 区分对象问题、方法问题与自身框架问题，避免把不同层次混为一谈。
- 区分事实、假设、暂定定义、推断与已验证结论，并保留可追溯证据。
- 将经过真实 Case 检验的有效结构、方法和经验，在明确适用边界的前提下积累、复用并继续检验。
- 在有证据需要时修正自身，同时避免无必要地重复造轮子或无限向基础理论递归。

## 明确不追求什么

本项目不试图建立解释世界的普遍理论，不预先设计完备且永久正确的方法论体系，也不假定存在对所有问题普遍有效的方法、框架或流程。任何治理框架都只是服务真实解题的阶段性产物。

## 实践记录原则

- **证据优先**：优先记录问题来源、上下文、实际操作、观察结果和失败过程，再抽象方法或理论。
- **状态明确**：明确区分事实、假设、暂定定义、推断和已验证结论，避免把推测写成定论。
- **来源可追溯**：为关键判断保留来源、日期、版本、执行者或相关上下文；引用外部材料时记录可访问的出处。
- **允许修正**：修改既有结论时说明变化内容、原因和依据，不以保持叙事一致为由掩盖反例。
- **可复核优先**：尽量记录足以让他人理解、复现或质疑过程的信息，包括约束条件和未解决的问题。

## 文档与版本控制

研究材料仍可随着真实实践增长而演化，不预设一套永久固定的研究目录；新增结构应服务于检索、追溯、复核或协作，而不是为了形式完整。治理层的固定入口与分层边界见 [`docs/README.md`](docs/README.md) 及 [`docs/vision/`](docs/vision/)。

Git 用于保存可审阅的研究材料和约束文件。操作系统文件、编辑器状态、临时文件、依赖目录、敏感配置以及生成的文档产物默认不纳入版本控制；具体规则见 [`.gitignore`](.gitignore)。

当某个生成文件本身是研究证据或需要长期复核时，应在提交前显式评估是否需要调整忽略规则，并在相关 Markdown 中说明其来源和生成方式。
