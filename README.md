# Method Engineering

研究方法如何被设计、组合、执行、验证，并通过真实实践持续演化，逐步形成可检验的 Method Engineering 知识。

## 目的陈述

本仓库记录与整理方法工程相关的研究材料、实践证据、执行记录、失败经验和逐步形成的知识。仓库以 Markdown 为主要表达形式，并可使用 JSON 等约束文件表达结构化信息、校验规则或机器可读的记录。

## 方向级成功边界

1. 研究从真实问题、案例、执行记录和失败经验出发。
2. 事实、假设、暂定定义与已验证结论保持可追溯区分。
3. 理论只在有明确问题来源或实践证据时逐步引入，并允许被修正或推翻。

## 记录原则

- **证据优先**：优先记录问题来源、上下文、实际操作、观察结果和失败过程，再抽象方法或理论。
- **状态明确**：明确区分事实、假设、暂定定义、推断和已验证结论，避免把推测写成定论。
- **来源可追溯**：为关键判断保留来源、日期、版本、执行者或相关上下文；引用外部材料时记录可访问的出处。
- **允许修正**：修改既有结论时说明变化内容、原因和依据，不以保持叙事一致为由掩盖反例。
- **可复核优先**：尽量记录足以让他人理解、复现或质疑过程的信息，包括约束条件和未解决的问题。

## 文件约定

仓库不预设固定目录结构。随着材料增长，可以根据实际问题和工作流演化出组织方式；新增结构应服务于检索、追溯、复核或协作，而不是为了形式完整。

建议在文件中自行标注：

- 材料类型：问题、案例、执行记录、失败经验、定义、假设、结论或开放问题；
- 证据状态：待核查、观察到、已复核、暂定或已验证；
- 时间与来源：记录时间、来源、版本和关联材料；
- 变更依据：为何新增、修订或撤回某项判断。

## 版本控制边界

Git 用于保存可审阅的研究材料和约束文件。操作系统文件、编辑器状态、临时文件、依赖目录、敏感配置以及生成的文档产物默认不纳入版本控制；具体规则见 [`.gitignore`](.gitignore)。

当某个生成文件本身是研究证据或需要长期复核时，应在提交前显式评估是否需要调整忽略规则，并在相关 Markdown 中说明其来源和生成方式。
