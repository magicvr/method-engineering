# 运行记录最小承载说明

本目录位于消费仓项目根，承载一条可追踪的方法需求从「待判定」进入判定起，直到接受并处理，或在形成承诺前以「不受理」终结的运行主线。工作区只是建立治理和交互规则的上下文，不是本目录的所有权边界；工作区关闭后，后续工作区和消费方仍可使用这里的记录。创建记录、发出回执或进行澄清本身不构成处理承诺；只有满足授权条件并将主记录转为「已接受」才形成承诺。它支持 Root D-002 v0.4.0 的最小状态、授权、响应、验证、交付、反馈、责任交接和退出语义；不承载 Goal 状态、审计 verdict、具体领域方法知识库或自动化调度。

## 目录约定

每条处理主线使用一个稳定的 `<work-item-id>` 目录：

```text
runtime-records/
├── README.md
└── <work-item-id>/
    ├── record.md
    └── events.md
```

`<work-item-id>` 优先复用需求方已有的稳定需求 ID；没有现成 ID 时，在当前消费仓内分配 `WRK-NNN-<slug>`。不要把工作区编号嵌入该 ID，也不要使用 `GOAL-*` 作为运行记录 ID。

不创建虚构示例处理记录或 Method Case；每个处理目录必须对应一条有可追踪来源的真实需求信号。若需追踪某次治理来源，记录可以引用相关 workspace/Goal，但该引用不改变运行记录的仓库级归属，也不成为 Goal 状态来源。

## 两个记录的职责

### `record.md`

这是处理主线的唯一当前运行状态来源。它至少要让读者能够核对：

- 需求边界、处理限额、授权责任和最低验证方向；
- 当前状态及最近一次状态转换依据；
- 需求方、授权人、Method Engineering 响应负责人、验证者和接收方的责任引用；
- 当前响应版本、验证安排/结论、交付版本、反馈路由和退出结果的引用或最小说明；
- 需要澄清的信息、范围/限额变更与双方通知的引用或最小说明。

「已接受」只记录已经确认的边界、责任、限额和开始响应的条件；具体响应的检索、判断、选择、复用、裁剪、组合、修改或形成发生在「响应中」。明确终结但未形成承诺的主线状态为「不受理」；该状态表示处理承诺没有成立，不等于对需求价值的判断，终结原因与责任方须能从当前主记录引用的事件依据中核对。

### `events.md`

这是追加式历史追踪记录，不拥有当前状态。每次需求回执与澄清、状态转换、授权、范围/限额变化、响应选择、验证分支、交接、消费方收件/验收/异议、反馈分类/回流和退出，都追加一条足以核对的事件说明，保留：

- 发生时间与责任人；
- 触发、转换前后状态和判断依据；
- 响应版本、验证条件/证据引用或反馈分类（如适用）；
- 结果、未决事项和下一责任。

即使事件中写有转换前后状态，也只能作为历史证据；当前状态必须读取 `record.md`，不得从事件末条推导或维护第二套状态。

## 最小运行流程

1. 收到有可追踪来源的方法需求信号时，建立同一处理主线并先记为「待判定」。创建记录或发出回执不代表接受处理承诺；提交者无需预先证明存在方法缺口。信息不足时可以澄清，但未获得接受前不启动候选方法、实验或无界研究。
2. 需求方/授权责任确认边界、限额、责任、授权和最低验证方向后，更新 `record.md` 为「已接受」，并在 `events.md` 记录授权依据；此时不要求已经选定具体响应。只有该转换形成处理承诺；它与 VP-001 的「已接受需求」和 IDLE 语义一致。
3. 若主线在承诺形成前终结，更新 `record.md` 为「不受理」，并在 `events.md` 记录终结决定、理由、责任方及通知情况。该终态可表示方法工程明确不接受、需求方撤回或双方同意终止；事件依据必须区分是谁发起及其原因。「不受理」不表示需求没有价值，也不等于「已退出」。信息不足、澄清中或没有收到回复时不得静默转为「不受理」；后续跟进期限按双方约定。
4. 开始具体响应工作时更新为「响应中」，记录响应责任、响应版本和选择/形成理由。
5. 形成可核对的候选响应与验证安排后更新为「验证中」。验证事件必须区分：通过；失败但原边界/限额不变；需要重新确认边界/限额；关键未知尚不能形成失败结论而等待信息。
6. 每次重要状态转换、决定、阻塞或需要需求方行动时，按双方约定的渠道与节奏更新当前状态、依据、下一责任人和下一次更新点。渠道与固定时限由具体协作约定决定；信息未齐或暂时没有状态转换时，不默认视为接受、拒绝或退出。
7. 已接受后收到范围、限额或责任变化请求时，记录变更及其来源；未重新确认前，不执行超出当前承诺的部分。仍可在原承诺范围内继续且安全时，可继续该部分；否则暂停受影响工作并由双方确认继续、调整或退出。不得以事件记录本身扩大授权。
8. 通过后更新为「已交付」，记录交付版本、接收方、适用条件和未决责任。响应包须足以交接：版本、适用条件、验证结论与证据、限制、未决事项和后续责任。交付、消费方确认收到以及响应验收/异议是不同事件；它们关联同一主记录，不新增运行状态。消费方验收不等于证明方法普遍有效。
9. 对响应的异议需说明其是否仍在原承诺范围内。范围内异议依原承诺处理并记录责任；范围外的工作须重新澄清并获得授权，作为新需求回到「待判定」。反馈先分类为对象问题、方法问题或运行机制问题，再记录处理路由；分类或事件本身不会自动产生新工作或恢复旧授权。
10. 已形成的处理承诺结束时记录退出原因、结果和未决责任，更新为「已退出」。退出不等同成功；已接受后由需求方撤回或双方同意结束，也记录为既有承诺的退出，不改写为「不受理」。尚未接受且未终结的请求，可由原需求方明确澄清或修订后沿用同一主线，并追加历史事件；修订本身不构成接受承诺。已接受后的范围、限额或责任变更按第 7 项重新确认；范围外的新工作、明确的新需求或「不受理」/「已退出」后的重提必须建立新的处理主线并进入「待判定」；原终态记录保持终结，不得复用或重置为活动记录，且不得自动恢复先前授权。新旧主线可相互引用；具体 ID 与引用字段仍待 I-005 决定。事件追踪保存历史；当前状态始终读取 `record.md`。

## 治理边界

- 本目录的运行状态不替代目标的 `status`、`progress`、信息门禁或审计台账。
- `record.md` 与 `events.md` 只记录本条处理主线；Goal 关系仍由工作区根下的目标五件套和 `goal-tree.md` 维护。
- 方法声明、假设、适用条件和已验证结论必须可区分；本说明不定义完整字段 Schema。
- 如需引用外部响应材料或验证证据，使用稳定路径/版本引用即可；不要因引用而新增强制对象或自动化流程。
