## D-006 · 信号登记时点与既有记录授权边界

### 用户裁决与依据

2026-09-26，针对 [A-008 F-001](../03-audit/A-008-r2-remediation-rereview.md) 所指出的建档时序缺口，用户选择「按 I-002 直接登记」。I-002 已授权 method-engineering 仓库范围内仅保存去标识化需求摘要、协议过程、响应/验收结果、实践仓库路径及提交引用，不保存原始个人或敏感资料；依据见 [E-008](../02-execution/E-008-r2-readiness.md)。

### 已接受的决定

1. 需要双方跟踪的可追踪真实需求信号抵达时，按 I-002 的既有最小留存范围立即创建「待判定」主记录并分配 work-item ID。沿用 D-004 的 method-engineering 根 `runtime-records/<work-item-id>/record.md` 与追加式 `events.md`，不在 WorldModel.ModernCultivation 克隆写运行记录。
2. 不新增逐条登记同意、签字或表单。超出 I-002 的留存范围时，仍须暂停相关记录并取得明确追加授权。
3. I-003 继续约束具体真实需求的处理授权；未取得该授权并形成「已接受」承诺前，不得开展方法响应、实验、无界研究或其他实质处理。登记、回执和澄清均不构成接受或处理承诺。承诺前撤回、明确不接受或双方同意终止时，仍按 D-002 留存「不受理」终态与依据；沉默或信息不足不能自动终结。
4. D-004 第 4 项原「处理授权后才分配 ID」假设由本决定替代；其试点宿主及边界选择不变。I-005 保持 non-blocking/open，具体字段、模板、ID、引用和渠道仍待真实信号与逐案协作确定；本决定确定时点，不虚构实际 ID。
5. 用户本轮再次确认 [D-005](D-005-consumer-delivery-choice.md)：交付目录、格式和工具由下游最终决定，可在首次提交时指定或澄清时确定；涉及仓库写入的精确交付路径、格式、工具与授权最迟在形成「已接受」承诺及任何写入前确认，首次提交不强制完整路径。无需文件交付时约定渠道。此为既有规则重申，运行记录登记沿用 I-002 与 D-004 已确认的范围及宿主，不以尚未确定的响应交付目录阻挡信号建档。

### 未选方案与门禁

不采用逐条新增登记同意的方案，避免重复既有 I-002 授权；不采用待 I-003 处理授权后才建档的方案，确保未获处理授权或提前撤回的信号仍可依 D-002 跟踪。两者均不扩大实质处理授权。

本次仅修正文档；尚无真实需求、实际 ID、运行记录或试跑事实。I-003 required/open、I-005 non-blocking/open、I-006 required/collecting 均保持；不预选 I-006 最终共享路径。A-006/A-007/A-008 的 findings 均不在此闭合，A-008 F-001 保持 open，待后续 independent 复审。Root active / 33%，R2 进行中且不放行，R3 未开始。
