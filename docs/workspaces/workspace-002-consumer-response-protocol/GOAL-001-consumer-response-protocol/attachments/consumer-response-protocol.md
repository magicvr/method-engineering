# 消费方需求—响应协议（试跑草稿）

本指南帮助需求方与方法工程一侧，从真实问题信号开始，明确处理承诺，完成有界响应、验证和交接。v0.1.3 已完成 R2 审计及消费方可执行确认；当前 v0.2.2 按 D-008 改为 WRK-001 的真实流程链，并按 D-009 限定入站材料为当前一条链的交接约定、实际往返材料和核对结论；该修订已由 self + 独立交叉复审（A-018 / A-019）确认，完整链路尚未执行。语义依据为 [R1 决策 D-002](../01-decision/D-002-runtime-record-boundary.md)。

本指南不提供特定领域方法，不承诺方法有效或普遍适用，也不规定消息工具、固定期限、完整记录字段或编号方案。以下步骤与问题清单是协作提示，不是新增的 Schema 合同。

## 谁负责什么

需求方说明实际困境、期待的变化，并确认响应是否满足约定；授权人确认可以处理的资料、范围和限额；方法工程响应负责人负责回执、澄清、承诺内处理和交接；验证者按约定检查响应；接收方确认收到的版本，并将验收或异议交给约定责任人。

同一个人可以承担多个角色，但每次授权、处理决定、验证结论和验收仍需明确以哪个责任作出。不能因为维护人相同，就把收到请求当成双方已经同意处理。开始前双方约定谁维护当前主记录、如何联系、何时更新和下一步由谁行动。

真实需求响应的交付目录、格式与工具由下游拥有最终选择权，可在首次提交时指定，也可在澄清时确定；方法工程可协助澄清，不得单方面决定。形成真实「已接受」处理承诺及任何真实响应写入前，双方须确认路径、格式、工具与授权。不需文件交付时，双方约定沟通渠道；完整交付路径不是首次提交的强制字段。本次 R3 已按 D-008 接受 WRK-001 的有界真实流程承诺；I-008 已核对下游承载与授权，并按 D-009 限定为当前 WRK-001 一条流程链的交接约定、实际往返材料和核对结论，不推广到领域方法交付或其他请求；实际交接结果另行记录。

具体交付目录由下游在相应真实需求澄清中确定；运行记录宿主选择不代替交付约定。

## 真实需求：按步骤协作

1. **提出真实问题。** 从实践中的困境、反复失败、难以判断的选择或期望改善的结果说起。给出可追踪的来源或联系上下文、问题所处情境、想改变什么，以及已知限制和可使用的资料范围。信息可以不完整；不知道的内容标为未知，交由双方澄清，不得编造。提交者无需先证明存在方法缺口，也无需先选定方法。
2. **收到回执并澄清。** 需要双方跟踪的可追踪真实需求信号抵达时，在 I-002 已有最小留存授权范围内立即创建主记录并分配 work-item ID，当前状态为「待判定」。不新增逐条登记同意、签字或表单，也不等待 I-003 的具体处理授权才建档。响应负责人确认收到了什么、还需澄清什么及下一责任人。建档、回执、澄清均不构成处理承诺；未取得 I-003 的具体需求处理授权并形成「已接受」承诺前，不开展方法响应、实验、无界研究或其他实质处理。双方约定沟通渠道、更新节奏及下一次更新点；缺信息或未收到回复不表示拒绝或退出。
3. **明确接受或承诺前终结。** 若承诺内的响应需要向下游仓库写入交付材料，先按下游最终选择确认交付路径、格式、工具与写入授权；I-002 范围内的 method-engineering 运行主记录依 D-004/D-006 承载，不受尚未确定的响应交付目录阻挡。无需文件交付时，双方约定沟通渠道。双方确认处理边界、限额、责任、授权和最低验证方向后，维护者记录依据并将唯一当前状态改为「已接受」，才形成处理承诺。此时可以尚未选定具体响应。若方法工程明确不接受、需求方撤回或双方同意在承诺前终止，则明确记录「不受理」，说明发起方、理由、决定依据和通知情况。「不受理」仅表示本次未形成承诺，不评价需求价值。不能因沉默或信息不足自动作此决定；继续跟进方式与期限由双方约定。
4. **在承诺内响应并沟通。** 开始具体处理时进入「响应中」，记录响应版本、负责人及选择或形成理由。重要决定、阻塞、状态转换或需要需求方行动时，按约定同步当前状态、依据、下一责任人和下次更新时间。收到范围、限额或责任变更请求时，先记录来源并重新确认授权；确认前不执行超出承诺的部分。原范围内仍可安全继续时可继续，否则暂停受影响工作，由双方确认继续、调整或退出。事件记录本身不能扩大授权。
5. **验证候选响应。** 有候选响应及验证安排后进入「验证中」，依据已约定的最低验证方向核对条件、证据和结论。区分验证通过、失败但原边界与限额不变、需要重新确认边界或限额，以及关键未知尚不能下结论。失败时记录后续处理责任；需要调整时回到授权确认；信息不足时补充或等待信息，不伪装为验证通过或失败。任何继续处理均受原承诺或新确认的授权约束。
6. **交付并分别确认收到与验收。** 验证通过后进入「已交付」，响应负责人向约定接收方交接下述响应包。分别记录交付版本与时间、消费方收到的确认、消费方验收或具体异议。发出文件不等于对方收到，收到也不等于接受响应；消费方验收只说明本次约定的满足情况，不证明方法普遍有效。尚未回复时继续按约定跟进，不能默认验收。
7. **处理异议、反馈与结束。** 双方先按原承诺核对异议：范围内由原责任人依承诺处理并记录下一步；范围外工作作为新需求重新澄清、授权，从新的「待判定」主线开始，不能自动加入旧承诺。反馈可先归为对象问题、方法问题或运行机制问题，再交相应责任人确认下一步；分类不自动启动工作。已有承诺结束时记录「已退出」，保留原因、结果、未决事项、下一责任及通知依据；退出不等于成功，接受后撤回也不能改写为「不受理」。

## 交接时带上什么

响应包应使接收方能核对：交付的是哪个版本、适用条件、验证结论及证据、限制、尚未解决的事项，以及交接后由谁负责什么。可引用稳定路径和版本，无需重复复制材料。将已验证结论、假设和待确认项区分清楚；不能用建议或期待替代事实。

消费方确认收到后，可明确表示「按约定接受」，或指出具体异议及其关联的承诺、响应版本和依据。若对异议是否在范围内存在分歧，先澄清并明确后续责任；在得到确认前，不以分类结论擅自扩大工作或宣称验收完成。

## 去哪里看当前状态

真实需求的唯一运行主记录位于 **method-engineering 仓库根**的 `runtime-records/<work-item-id>/record.md`，同目录 `events.md` 只追加历史；按 [D-006](../01-decision/D-006-signal-intake-record-timing.md)，可追踪真实需求信号抵达且需要双方跟踪时，在 I-002 既有最小留存范围内立即建立「待判定」主记录并分配实际 work-item ID；WRK-001-world-model-demand-method 已由原需求方明确修订为跑通链条，并依 D-008 / EV-003 接受这一有界流程请求；原领域需求仍未完成。记录引用 WorldModel.ModernCultivation 实践仓库路径与获准留存的提交引用，候选克隆中不创建运行记录文件。这是用户针对本次试点批准的有界宿主例外，不改变一般消费仓根目录的运行记录所有权约定；见 [D-004](../01-decision/D-004-trial-runtime-record-host.md)。

一条主线只有一个当前状态来源：按既有运行记录约定，由 `record.md` 维护当前状态，`events.md` 追加回执、授权、变化、交付、收件、验收、异议和退出的历史依据。事件不构成第二状态源，也不能仅凭最后一条事件推导当前状态。交付、收到、验收和异议是同一主线上的不同事实，不新增运行状态。

「不受理」与「已退出」均保留为终态，不重置为活动记录，也不改写既有终结事实。后续重提或新需求另建主线，从「待判定」开始；新旧主线可相互引用，旧授权不会自动恢复。

## 本次试跑的材料边界与指南位置

整个 method-engineering 仓库（包括工作区附件、runtime-records 下的 record.md 与 events.md）仅保留去标识化需求摘要、协议过程、响应与验收结果、实践仓库路径和提交引用；仓库任何位置均不得留存原始个人或敏感材料。责任与参与者使用角色标签或责任引用，避免直接身份标识。未知输入先标记并澄清。上述 I-002 既有授权允许范围内的信号登记，无需新增逐条登记同意、签字或表单。记录、回执和澄清不构成接受或处理承诺；实际处理仍须 I-003 具体授权和「已接受」承诺。已有仓库使用与记录授权不替代对具体需求的处理授权；若需要超出该留存范围，须暂停相关记录并取得用户明确追加授权后再继续。

本文件是 R2/R3 过程中的唯一协议草稿，不复制全文到候选试跑仓库。R3 试跑验收与指南验证后、Root 关门前，须按用户届时确认的本仓共享运行文档路径升格唯一全文；最终路径尚未确定，升格后工作区仅保留治理证据与指向。

## 提交前可选问题清单

这些问题供需求方整理思路，不要求逐项填表；无法回答的内容可直接标为未知。

- 我在什么真实情境下遇到什么困难，希望改变什么？
- 哪些资料可以使用，哪些内容不能复制或公开，谁能授权？
- 我已知哪些限制，还需要双方澄清什么？
- 怎样的最小检查能帮助判断这次响应是否有用？
- 谁接收响应、谁验收或提出异议，如何联系和更新？
- 我希望使用什么交付目录、格式和工具？可以先留待澄清，涉及写入时须在接受承诺和写入前确认。

## R3 专用：WRK-001 真实对接链条

D-008 取代 D-007 的合成演练安排。当前真实目的就是跑通一次对接流程；用户明确修订未接受非终态请求后，沿用 WRK-001，保留历史。未承诺请求的修订本身不代表接受；本次由 D-008 逐项核对范围、限额、角色、授权和最低验证方向后，才形成「已接受」承诺。已接受后的变化按 D-002 第 7 项确认；范围外新工作和终态重提另建主线。

1. **落实同一条需求交接。** 下游选择 exchange/WRK-001/，遵循其文件命名、Markdown UTF-8 无 BOM LF、多轮并存、人工核对约定。原文由下游留存；摘要重建必须标「摘要，非原文」。不得将旧领域需求冒充本次流程需求。
2. **回执与授权。** 方法工程实际读取交接并确认版本/来源；本次具体授权与接受条件见 D-008，唯一主记录已接受。将实际澄清、角色和下一责任连到同一追踪线；不因接受记录而声称此前下游材料已经送达。
3. **形成并核对响应。** 响应仅为本次可用的交接约定、往返材料和核对结论；按实际开始、形成核对安排的事实更新「响应中」「验证中」，不补造阶段。响应包交代版本、适用条件、验证结论与证据、限制、未决事项及后续责任。
4. **交付与实际收件。** 通过核对后交付；消费方实际取得这份材料并核对来源/版本后，单独确认收件。交付、收到、验收不能互相代替，不预填对方回执。
5. **验收、反馈与结束。** 消费方按协议可读性、引用可达性和交接责任给出接受或具体异议；响应方实际接收反馈，分类并明确范围内处理或范围外重新澄清的下一责任，再记录结束。没有回复不自动验收或退出。
6. **证据与关门。** 两侧实际消费同一份交接才构成链路证据；不拼接各自 walkthrough。同一人承担消费方与方法工程角色时逐次记录角色切换，不声称独立团队共识。执行台账只记录已经发生的动作；下游治理事实由其 E 条目引用材料，不镜像上游当前状态。

I-003/I-008 verified 仅证明本次授权与安排就绪（I-008 的材料范围按 D-009 限于当前 WRK-001 一条流程链）；R3 尚未完成。原领域方法需求未交付，下游 Root/VP 与成功标准不受本次接受影响。R3 验收与指南验证后，仍须按 I-006 由用户裁决本仓共享路径、迁移唯一全文，并完成关门审计。
