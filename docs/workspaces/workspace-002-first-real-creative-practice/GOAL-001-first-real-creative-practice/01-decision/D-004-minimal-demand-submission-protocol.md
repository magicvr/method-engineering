# D-004 · 小波次最小真实需求提报协议

## 决策

本小波次允许 book_green 按真实创作需要提报方法/工具需求。提报协议只规定 Method Engineering 判断一条真实需求所必须知道的最小内容，不规定固定模板、文件格式或沟通方式。

首轮提报至少包含以下三类内容：

1. **真实问题**：当前实际发生了什么问题、卡点、不确定性或需要作出的判断；应尽量说明它发生在创作的哪个位置。
2. **现状证据**：能够支撑问题判断的当前状态、具体案例、作品材料或可定位引用。没有现成文件时，可以用事实描述说明发生了什么；不要求先整理成正式文档。
3. **希望获得的帮助**：希望 Method Engineering 帮助回答、选择、构造、检验或改进什么；如果预期结果尚不清楚，可以直接说明尚不清楚，不要求先提出方法方案。

以下内容本协议不要求：联系人、固定渠道、固定节奏、响应时间、回复模板、完整项目背景、完整协作者名册、预先存在的验收标准、预先指定的下一阶段或作品方自行设计的解决方案。

## 运行边界

- 提交可以是自由文本或作品仓已有的自然记录；“协议”约束的是内容充分性，不是格式。
- 收到提报只表示进入需求澄清与判断，不表示需求已被接受，也不自动授权方法响应。
- Method Engineering 只在真实提报无法被理解、界定或判断时，针对实际缺口提出补充问题；不得预先扩充字段。
- 一条真实需求只有在被接受且具有独立的方法工程范围、交付证据或判断/审计边界时，才在本 Root 下创建直接子目标；普通澄清、反馈和运行记录不单独创建 Goal。
- 若后续真实案例证明这三类最小内容不足以完成判断，再以该案例为依据追加协议字段并记录新的决策；本协议不追求一次性完备。

## 范围与门禁关系

本协议只适用于 VP-002 的当前小波次和 book_green 的真实需求入口，不改变 VP-002 的方向级终点、Root S1/I-003 作为作品创作边界探索与 S1 退出条件的角色，或四周投入上限。I-003/D1 不再是局部方法需求响应的统一门禁。它允许需求提报先发生，但不把 Root S1、S2 或任何具体方法响应写成已通过。

## 消费者可见副本

已将本协议的运行副本交付到 `book_green` 仓的 `runtime-records/request-intake.md`（v0.1.0），并同步更新其 `runtime-records/README.md` 入口。该副本是作品仓实际提报时可读取的操作说明；本文件仍是 Method Engineering 侧的决策与边界记录，不与作品仓的运行记录形成第二套当前状态源。外部副本当前已写入 `book_green` 工作树但尚未提交固定 Git 版本。

## 选择理由

将协议作为 Root 的波次级决策落盘，而不是在 GOAL-002 下新建子目标：GOAL-002 负责真实作品信息登记与 D1 信息就绪；需求提报协议服务整个小波次的运行入口，当前规模也不足以形成独立目标的实施、验收和审计范围。
