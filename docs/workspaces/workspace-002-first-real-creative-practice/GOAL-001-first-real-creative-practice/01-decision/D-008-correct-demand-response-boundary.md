# D-008 · 修正需求响应责任并解除 D1 对局部方法需求的统一门禁

## 决定

根据维护者选择的方案 A，VP-002 和 workspace-002 的当前语义改为以下闭环：作品仓在正常创作中提出可以粗略的真实需要或问题信号；Method Engineering 主导需求澄清、问题界定、方法/工具研究、设计、构建、内部验证和交付；作品仓在正常创作中使用交付物并反馈实际现象、影响和预期；Method Engineering 负责诊断、修正和再次交付。

作品仓提供创作事实、目标、限制和使用反馈，不承担方法的工程化分解、候选设计、方法验收方案、根因诊断、候选比较或工程证据整理。若确需额外比较实验，由 Method Engineering 设计并明确征得参与同意，不把它作为默认使用义务。

D1 继续承载作品自身的创作接受条件、范围、终点和下一阶段探索。D1 未完成不再作为所有局部方法需求的统一前置门禁；足够具体且局部有界的需求可以与 D1 并行或局部交错进入 S2。D3 仍依赖作品方对最终大纲的接受。

GOAL-003 当前只保留为已接收的“元规则”需求信号与需求澄清目标；其旧的 D1 前置方法分析授权和候选构建路径不再是当前工作。历史 D-005～D-007 及既有执行条目保留为过去发生的记录，本决定只取代其当前操作解释，不重写过去。

## 理由与影响

此前把 VP-002 D1 的作品接受边界探索和 Method Engineering 的方法构建放入同一前置链，导致作品仓在获得方法支持前被隐含要求共同定义方法问题、候选和验证方式。该安排偏离 VP-001 的需求驱动闭环，也使本仓与作品仓的职责边界发生倒置。

修订后，GOAL-002 仍可继续探索作品自身的大纲接受边界，Root S1 仍保持进行中；但 S1/D1 的未决只影响 S1 退出和 VP-002 的最终关门，不统一阻止一个已经足够具体的局部方法需求。GOAL-003 的 P2 改为由 Method Engineering 主导澄清和最小事实收集，尚未形成具体方法响应时不构建猜测性方法。

本决定不修改 Charter，不改变 VP-002 的方向级终点，不声称方法响应、试用、作品使用或作品验收已经发生。
