## 决定

形成一份可直接发送给真实作品仓/作品方的首轮信息请求。请求只用于确认真实状态、边界、责任和投入限额，不要求作品仓改造自身创作流程，也不提前询问 S2 的具体方法需求。

首轮允许部分字段暂缺，但每项必须标注状态并提供可核对来源。收到后由 Method Engineering 逐项判断完整、缺失、歧义、冲突或超范围内容，再生成下一轮的补充/澄清请求；单次提交不自动关闭 Root 信息项。

## 可直接发送正文

### 主题

VP-002 首个真实作品实践：首轮信息确认请求

### 正文

你好。为了确认这次实践是否落在你们当前真实创作阶段，并定义一个双方都能核对的有界范围，请基于作品仓当前的实际状态提供以下信息。

首轮不要求一次性完美回答；每一项请标注 `已确认`、`暂定`、`不适用` 或 `待补充`，并尽量提供可核对来源，例如仓库路径、URL、分支、tag、commit、版本号、文件路径或确认日期。若某项暂时无法提供，请明确写“待补充”及预计何时可以确认，不要用推测替代事实。

这不是要求你们把创作过程改造成预设流程。我们会以作品当前真实状态和你们实际的下一创作阶段为准。如果你们当前下一阶段并不是“包含故事线规划、足以进入下一创作阶段的大纲”，请直接说明；我们会暂停本轮范围确认并重新判断方向，不会扩张“大纲”定义或要求作品适配预设流程。

#### 1. 作品仓身份与当前状态

请提供：

- 作品仓名称、稳定 URL 或本地路径，以及能够代表本次实践的分支、tag、commit 或版本号；
- 上述版本/状态对应的确认日期；
- 当前真实创作状态：已经完成什么、正在推进什么、下一步原计划是什么；
- 与本次确认有关的文档、素材或目录路径；
- 谁确认这组信息，若有不确定项请标出。

#### 2. 本次大纲的范围与起点

请提供：

- 本次大纲要覆盖的内容，以及希望形成的具体成果；
- 明确排除的内容（本轮不处理什么）；
- 作品当前起点：将从哪些已有文档、素材、版本或创作状态开始；
- 已知的硬约束、依赖或不能改变的条件。

#### 3. 固定终点与接受条件

请提供：

- 对“包含故事线规划、足以进入下一创作阶段的大纲”的本作品具体定义；
- 作品方认为最低可接受的检查项或成果特征；
- 该大纲被接受后，作品实际要进入的下一创作阶段；
- 谁负责最终接受，接受将通过什么方式留下记录（例如文档确认、评阅意见、Issue、PR 评论或其他明确记录）；
- 哪些反馈或修订仍属于本次范围，哪些反馈将视为超出范围。

#### 4. 责任边界与反馈交接

请提供：

- 作品方/作品仓的联系人、创作决策人和评阅/接受人；
- Method Engineering 在本次实践中的责任边界，以及不负责的事项；
- 其他协作者的角色（如有）；
- 提交、评阅、提问、反馈和交接分别通过什么渠道进行；
- 反馈的基本节奏、响应责任和变更如何被记录；若暂无固定节奏，请说明实际可行方式。

#### 5. 本次实践的投入限额

请提供或共同确认：

- 作品方可投入的时间窗口、轮次、工作量或其他等价上限；
- 希望 Method Engineering 遵守的工作节奏或投入上限（如已有约定）；
- 如果工作接近或超过上限，如何暂停、重新评估或由双方明确批准扩展；
- 本轮限额的确认人和确认日期。

#### 6. 回复格式

可以直接按以下表格回复；不适用的项目请写 `不适用`，暂时无法确认的项目请写 `待补充` 并说明原因和预计复核时间。

如涉及敏感内容，不需要一次性发送整个仓库；请优先提供稳定版本引用、必要的文件路径和经处理的摘要，并注明省略或脱敏范围。后续若确实需要固定共享资料，我们会另行登记来源、版本和哈希，不把未固定的候选路径当作事实依据。

收到首轮回复后，我们会返回一份逐项结果：已足够、缺失、需要澄清、存在冲突或超出本轮范围的项目，并只对后几类提出针对性的补充请求。首轮回复本身不等于 Root S1 已通过。
