# D-003 · 将首轮信息请求收缩为最小可运行集

> 本版本未发送，已由 D-004 替代。保留本条作为上一轮“最小可运行集”裁决的历史记录。

- **日期**：2026-09-18
- **状态**：accepted
- **决策来源**：用户选择“最小可运行集”。
- **交付状态**：已生成、待发送；本条记录不表示真实作品仓已经收到或回复。

## 决定

1. 首轮只要求完成 VP-002 D1 和 Root S1 所需的最小事实：作品仓身份与当前状态、范围与起点、固定终点与接受条件、角色级责任与最小交接方式、投入限额。
2. 角色级责任只需说明作品方、Method Engineering 及必要协作者分别负责什么，以及如何表示“可以开始 / 需要反馈 / 已接受”；不要求联系人姓名、固定沟通渠道、详细响应节奏或完整协作者名册。
3. 不要求一次性提供整个作品仓或与当前门禁无关的资料。只有实际运行证明某项细节影响实施、反馈闭环或门禁时，才发起针对性补充请求。
4. Root I-004 仍是 required；本轮只收其最小可运行核心，收到后仍需逐项审视是否足以支撑 S1。缺口不能被“未要求”自动视为已关闭。
5. 若真实作品当前下一阶段不符合 VP-002 已冻结的终点，立即停止扩张请求并回流 `/vision`，不改写“大纲”语义。

## 理由与取舍

宽版请求包含联系人、详细渠道、节奏和协作者信息，虽然便于格式化协作，但尚未证明是完成 VP-002 D1 的必要事实。精简首轮可降低作品方负担、减少无效信息收集；代价是实际运行中若出现交接缺口，需要再发起补充请求。该代价符合本目标原定的迭代式收集流程。

## 可直接发送正文

### 主题

VP-002 首个真实作品实践：最小首轮信息确认请求

### 正文

你好。为了用尽可能少的信息确认这次实践是否落在你们当前真实创作阶段，并定义一个双方都能核对的有界范围，请基于作品仓当前实际状态提供以下五组信息。

首轮不要求一次性完美回答；每一项请标注 `已确认`、`暂定`、`不适用` 或 `待补充`，并尽量提供可核对来源，例如仓库 URL/路径、分支、tag、commit、版本号、文件路径或确认日期。暂时无法确认的内容请写“待补充”，不要用推测替代事实。

这不是要求你们改造创作流程。我们会以作品当前真实状态和你们实际的下一创作阶段为准。如果当前下一阶段并不是“包含故事线规划、足以进入下一创作阶段的大纲”，请直接说明；我们会暂停并重新判断方向，不会扩张“大纲”定义或要求作品适配预设流程。

#### 1. 作品仓身份与当前状态

- 作品仓名称、稳定 URL 或本地路径；
- 能代表本次实践的分支、tag、commit 或版本号，以及对应日期；
- 当前真实创作状态：已经完成什么、正在推进什么、下一步原计划是什么；
- 与本次确认有关的文档、素材或目录路径。

#### 2. 本次大纲的范围与起点

- 本次大纲覆盖什么，预期形成什么成果；
- 明确排除什么；
- 从哪些已有文档、素材、版本或创作状态开始；
- 已知的硬约束、依赖或不能改变的条件。

#### 3. 固定终点与接受条件

- 对“包含故事线规划、足以进入下一创作阶段的大纲”的本作品具体定义；
- 最低可接受的检查项或成果特征；
- 接受后作品实际要进入的下一创作阶段；
- 由哪一类角色负责最终接受，以及接受如何留下可核对记录；
- 哪些反馈仍属于本次范围，哪些反馈超出范围。

#### 4. 最小责任边界与交接方式

只需说明角色级的最小约定：

- 作品方负责提供哪些创作事实、作出哪些创作决定；
- Method Engineering 负责支持什么、不负责什么；
- 若有其他角色会影响本次接受，只说明其角色和责任；
- 用什么最简单的方式表示“可以开始”“需要反馈”或“已接受”。

本轮不要求联系人姓名、固定沟通渠道、详细响应时间或完整协作者名册；如果这些内容在实际运行前确实成为门禁所需，再单独补充。

#### 5. 本次实践的投入限额

- 作品方可投入的时间窗口、轮次、工作量或其他等价上限；
- 如已有约定，Method Engineering 应遵守的投入上限或工作节奏；
- 接近或超过上限时如何暂停、重新评估或明确批准扩展；
- 限额的确认角色和确认日期。

可以直接按以下表格回复；不适用的项目请写 `不适用`，暂时无法确认的项目请写 `待补充` 并说明原因和预计复核时间。
