# D-029 · 修正两处编排器缺陷：冻结状态的基线引用与记录中的文件行数

## 缺陷一：续跑状态冻结 01 的**方法基线引用错误**

- **事实**：[续跑状态冻结 01](../attachments/continuation-state-frozen-01.md)（写作于 run-09 之后、独立审计之前）声明「方法一律以方法候选 **v0.15.1**（指纹 `E4C74617…`）为准」。此后方法升为 **v0.16**（按 A-001 的最小闭合修正）与 **v0.16.1**（G.3／出口第 8 项门禁一致性修正），而 **run-10 是在 v0.16.1 上执行的**——**差异恰好落在 G.3 与出口退回检查第 8 项**，即本次要判的**收束门禁**。
- **发现者**：**run-10 的隔离执行者**——它把这一点列为「**本次唯一需要上级处置的输入不一致**」，**按任务指定的 v0.16.1 执行**，并明确声明：**若上级认为应以 v0.15.1 判定，则本次「收束」结论不成立**（v0.15.1 的旧停止条件在 run-09 已被判不成立）。
- **裁定**：**run-10 的判定基线为 v0.16.1**（创作者已授权在 v0.16.1 上恢复续跑）；冻结 01 中的 v0.15.1 引用**属编排器缺陷**（该文件写作时方法确实是 v0.15.1，但它在 run-10 被当作继承输入时**未同步基线**）。
- **修正**：① 在冻结 01 内加「已更正」注记（保留原文）；② 另立 **[续跑状态冻结 02](../attachments/continuation-state-frozen-02.md)**（run-10 后；基线＝**v0.16.1**）**取代**冻结 01 作为继承输入。

## 缺陷二：记录中的「文件行数」字段**系统性偏低**（统计口径/编码问题）

- **事实**：此前多处记录用 PowerShell `Get-Content` 统计行数；该方式在本仓库的 UTF-8 文件上出现**编码误判**（控制台曾把同一批文件显示为乱码），所得行数**系统性偏低约 38%**。例：v0.12.1 记为 175 行、**实为 281 行**；v0.16 记为 242、**实为 394**；v0.16.1 记为 250、**实为 405**。（两处独立发现：run-06/run-11 类执行者报告的行数一直是对的，本次由编排器复核发现自身字段有误。）
- **影响面**：D-013／D-016／D-018／D-021／D-022／D-023／D-024／D-027／D-028 与 E-022／E-024／E-025／E-027／E-031／E-033／E-034／E-035／E-040／E-041 等记录的「N 行」字段，以及若干运行记录中的版本描述。
- **处置**：
  1. **以 `sha256` ＋字节数为权威**——这两项**不受该缺陷影响**，且各版本均已记录在案；
  2. 公布**权威行数表**（下表；统计口径＝按 UTF-8 解码后按 `\n` 分行、去掉末尾空行）；
  3. **修正近期仍在用的记录**：**D-027／D-028／E-040／E-041** 的行数字段改为权威值；
  4. **更早记录的行数字段由本表取代**，不再逐条改写（避免为纯记账字段大规模改写历史记录）；但**不得**再据旧行数作任何核对依据（**核对一律用 sha256／字节数**）。
