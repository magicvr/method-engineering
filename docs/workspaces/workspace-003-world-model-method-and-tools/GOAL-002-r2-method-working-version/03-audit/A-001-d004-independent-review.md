## 结论

- **W1 的总体路线正确**：先建立「需求条款 → 方法必须回答什么 → 哪些地方存在设计选择」的中间层，而不是一上来按需求直接写方法。W1 的出口定义与其职责一致——只声称完成映射与登记，并明确说明候选结论尚未产生。**可以承认「条款映射与差异登记已经完成」。**
- 但**不建议 `D-004` 原样进入下一步**：先做一轮**小修**，再把它作为 W2 的输入冻结。

## Findings

- **`A-001-F-001`（required）**：现「直接采纳」列**混合了两类内容**——① 需求直接规定的约束（机制/状态分离、五类裁决返回、禁止结果补丁等）；② **助手推出的实现方案**（例如 §4.3 从"裁决应可追溯"推到"落为一次裁决的最小记录"、§7.3 从"允许未定义"推到"必须显式登记未定义"）。后者合理，但已属**方法设计响应**，不是需求原文自身。
  **关闭要求**：把 `D-004` 的逻辑拆成三层——**原文硬约束 → 对方法产生的要求 → 尚未决定的实现方式**；避免 W1 悄悄替 W2 定设计。
- **`A-001-F-002`（required）**：`E3` / `C1` 把 §4.1「模型依赖与组合」、§5.1「能力发现」、§7.5「兼容与冲突」合并为"一处权威清单/索引"**过头**。三者只是**相关**：能力目录回答"能裁决什么"，模型依赖回答"模型之间怎么组合"，冲突登记回答"哪里存在未解决的一致性问题"。**过早假定它们共用一个权威索引，本身已经是一个架构方案。**
  **关闭要求**：`E3` 改写为「存在承载与交叉引用上的关联，需要 W2 决定是否统一」，而不是先认定"重叠"。
- **`A-001-F-003`（required；重要）**：`C3` 存在**语义降级**风险。§9 已被本映射自身理解为「新模型最低要求 **11 项**」，但 `C3` 又问"哪些必填、哪些可标待定"，并倾向只保留一个更小的"最小必填集"——这会自行缩减原文的最低要求。
  **关闭要求**：改问为——**11 项均必须被处理**，但**哪些项目允许以「未知 / 尚待验证 / 不适用」作为显式结果**，以及**这种未完成状态是否会阻止模型注册、或限制其可声明的裁决能力**。
- **`A-001-F-004`（required；重要）**：`C4` 不宜表述为「逐条记录 vs 按能力段落记录」的二选一。§11 要求能识别"哪些过去裁决依赖旧版本、哪些需要重新计算"，而 §4.3 已要求裁决结果保留模型版本等追溯信息。真正不可退让的是一个**不变量**——**过去裁决必须能够追溯到其使用的模型版本**；至于每条裁决直接记、建立反向索引、还是按能力维护索引，属**实现技术**。
  **关闭要求**：把 `C4` 从"存储粒度二选一"改为「**先确定追溯不变量，实现方式可后定**」，避免选出一个成本低、却满足不了 §11 的方案。
- **`A-001-F-005`（required）**：`C1`～`C8` **不应全部提升为同等级的"创作者裁定"**。`C2`、`C3` 这类会改变方法**语义**的选择确应升级裁定；但 `C5`（是否合成一页）、`C8`（登记位置是否指定路径）、乃至 `C7`（是否单设一节），相当部分只是**方法工程内部的结构设计问题**。即使 `D-003` 规定最终结论由创作者决定，也不代表助手应把所有文档组织决策都抛回需求方——否则会形成新的**人类审批瓶颈**。
  **关闭要求**：助手先依据约束给出**默认设计**；**仅在涉及语义、责任边界、成本等级或不可逆承诺时**升级给创作者裁定；据此把 `C1`～`C8` 分为「需要创作者裁定」与「助手可自行设计、创作者审阅」两类。
  **附注**：本项会修改 [`D-003`](../01-decision/D-003-executor-boundary-revision.md) 所确立协作规则的**适用口径**（哪些判断升级、哪些不升级），属创作者裁定事项。

## 肯定与保留（非 finding）

- **§3 的识别**：没有因为 W1 名义范围写作 §4～§11、§13，就把「按需扩展、没有真实需求不主动建模」这一**主循环**丢掉——这是在**做需求分析**，不是机械抄表。
- **W1 与 W2 分开**：明确写了「裁定前不得把候选结论写入方法正文」，符合「W1 建立需求约束空间，W2 才开始设计方法」的节奏，应予保持。
