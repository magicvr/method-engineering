### Findings

#### F-001 · 验收步骤还不能判断回答是否成立

- 严重度：high
- 建议：required
- 状态：open

D-029 把「可登记、可验证，且验证依据是模型实际回答行为」定为冻结前必须补上的边界。草案第 33–39 行把登记写成一组字段：问题族标识或描述、输入条件、期望输出类型、依赖的机制或状态、适用范围与拒答条件、版本与扩展状态。第 37 行要求每个问题族另有代表性查询、期望答案类型、追溯、通过/失败判据、停止或拒答处理。正文没有写出通过/失败判据的内容。

因此下面三种结果都能走进草案 §6 的正向路径：登记行已填；模型产出了一段类型相符的文字；再增加一个问题并声明检查了旧回答。路径不要求证明三件事：回答由已采纳的机制和状态推出；该问题族对应获准真实需要的哪一部分；改变一个相关条件后，回答按已写明的理由发生变化。第 38 行只把「有登记却无法回答」定为失败，不能挡住无依据的回答。

VP-003 意图第 2 项已经要求方法工作版覆盖条件敏感性验证。R1 v0.6.4 §1 要求结果有机制依据、不伪造精度，并在现有能力足够时停止建模。草案 §6 用「一个新增问题及其对既有回答的影响」代替这些检查，又没有写明旧检查继续有效。登记字段齐全加一次有文字的回答，会再次变成能力通过。这正是 D-029 禁止的签字式登记。

闭合需要草案自己写明可执行规则：什么叫回答成立，什么叫问题族偷换了获准需要，什么叫条件变化已检验；并写明登记行填满不是通过。

#### F-002 · 「长期可用」没有通过标准

- 严重度：med
- 建议：required
- 状态：open

开篇承诺的是可长期使用、可按需扩展的世界模型机制。§6 的通过展示是一条链路加一次复用、一个新增问题。同节写明一次运行不证明永久有效，并以可复用、可维护、可演化的实际表现检验「长期可用」，但没有定义这三项的观察标准。冻结后，「长期可用」既是承诺，又被声明为本次验收不能证明。验收尺度因此不确定。

闭合需要二选一，并写进承诺正文：把冻结承诺收束到一次复用和一次增量扩展所能证明的性质；或者写明在使用「长期可用」之前还要看到哪些可重复观察。两句不能同时作为验收依据。

#### F-003 · 服务对象宽于仍要求保留的对象，保留项不能执行

- 严重度：med
- 建议：required
- 状态：open

草案 §1 把服务写成：帮助只有部分、模糊或不一致设定的创作者，逐步回答可抽象为「这个世界是怎样一个世界」的一系列问题，并长期组织、调用和演化设定。R1 v0.6.4 §1 的对象是创作中有边界的客观世界问题：给定条件下的机制、世界状态或交互结果能否裁决，以及确有机制缺口时如何以最低必要成本补足。同节排除剧情大纲、主题选择、宏观历史演化、完整世界模拟器等十一项，并要求世界状态、角色所知、观众所知分开，方法不写 canon。VP-003 的触发是创作中的客观裁决需求，非目标包括不替下游做世界观设定或 canon 裁决。

草案 §9 写「保留对象与非目标」，同节又把 VP-003 是否澄清留作未确认。§10 把「确认上述入口与能力范围」和「确认 VP-003 澄清」放在同一次裁决里。§1 与 §9 同时生效时，验收者无法判断宽服务句和十一项排除谁优先。§10 的缺口次序、现有能力足够则停止建模、条件敏感性，也不在 §9 的保留清单里。只保留一个标签，后继验收会把草案 §6 当成完整尺度。

闭合需要：在用户书面确认 VP 澄清之前，承诺正文中的服务对象与 R1 §1 / VP-003 的客观裁决对象一致；把继续有效的排除、缺口次序、停止建模和条件敏感性写成可核对条目；把 VP 范围裁决与能力文本裁决分开。用户若采用更宽对象，须单独书面确认，并说明十一项排除如何处理。

#### F-004 · 草案要求确认的界限本身没有内容

- 严重度：med
- 建议：required
- 状态：open

§10 要求用户确认候选设定的允许边界、首轮投入上限，以及「复用＋增量扩展」的验收底线。候选边界和投入上限在 §1–§9 没有提案。§8 允许明确标注的候选、假设与条件分析，没有数量、轮次或可引入新设定的界限。§6 的「复用＋增量扩展」也只有一次复用和一个新增问题，和 F-002 的「长期可用」并立。

这三项会改变什么算通过：方法可以引入多少尚未由作者决定的设定，一轮交互做到哪里必须停止，一次扩展是否够格。它们现在是空白必填项。确认动作无法在空白上发生。

闭合需要草案写出拟采用的界限，或把尚未定义的两项移出冻结门禁并标明 non-blocking 与复核触发。留在 §10 的每一项都要有可同意或可改的正文。

#### F-005 · 失败清单中的交互条款可以倒转 D-029

- 严重度：med
- 建议：required
- 状态：open

§7 的句首是「以下情形不得按原承诺验收」。同列有「把运行时交互本身当作失败」。这一列其余各项都是交付状态：核心工作退回创作者、只有记录、不能回答、虚构设定。中间这一项是评价方式。按清单字面执行时，它可以被读成：运行中出现了交互，因而不得验收。该读法与草案「运行时交互允许」、§6「运行时交互本身不是失败」以及 D-029 第 1 项相反。

闭合需要把这一项移出产品失败清单，改写成单独的无效否决规则：不得因发生了运行时交互而判定能力失败。产品失败清单只保留交付状态。

#### F-006 · 适用层级没有写明

- 严重度：med
- 建议：required
- 状态：open

§9 废弃 v0.6.4 的三类验收用法：重复确认、材料齐全即能力就绪、未知一律整体停止。R1 检查点已经由 D-018 / E-034 / A-005 按协议冻结关门。R2-W（GOAL-009）与 R3（GOAL-010）已关门。R4（GOAL-011）的 RUN-001 已按显式失败记录，交付仍受 I-004 阻断。草案同时要求保留历史冻结事实。它没有写这组新验收句约束哪一层：不重开已关门检查点，不把 RUN-001 改判为通过，也不自动放行 R4。

「未知一律整体停止」若不加范围，还会盖过 v0.6.4 §1 中仍然有效的停止：授权不足、证据不足以分类、现有能力足够因而停止建模。§8 只保留了权限不足和必须由作者决定的设定。

闭合需要一段适用声明：历史关门事实保持原判；本承诺只约束此后的能力验收与方法修订；列出继续有效的停止条件。适用声明写明之前，§9 不能当作验收依据。

#### F-007 · 附件状态与决策状态不一致

- 严重度：low
- 建议：recommended
- 状态：open

附件 frontmatter 为 `status: active`，标题写「草案，待用户确认」，D-028 为 `decision_status: proposed`。只读附件时会把它当成已生效承诺。

闭合需要附件状态与 D-028 同为草案或 proposed，直到用户书面确认冻结。

### 与既有意见的异同

A-004（independent / pass）审查的是 v0.6.4 协议完整性，当时的范围就是协议与交付契约，不要求方法已经跑通。A-005（self / pass）关闭的是该协议阶段。本条不撤销这两次结论。F-006 要求草案明示这一点。

A-007（independent / pass）只覆盖 reframe 的历史保全和门禁隔离，没有审查本草案。本条与 A-007 无结论冲突。

D-027 所附复审建议的最小链路是「尚未结构化需要 → 可裁决问题 → 局部模型 → 创作可用结果」。E-044 记录用户随后把主承诺改为构建世界模型，裁决能力改为验收条件，问题拆解改为辅助。本条接受这一已记录修正，不要求把拆解改回主产品。F-001 要求的是：辅助拆解仍然要服务于获准需要，并且回答要有依据。

D-028 的推荐链路没有单列运行时交互；附件 §6 已列入。在 D-028 与附件对齐之前，以附件 §6 为准，同时受 F-005 约束。

### 结论 + 建议给编排器/用户的下一步

conditional。方向已经写对：主承诺是世界模型，裁决能力是验收条件，运行时交互允许，字段和签字不能代替通过，历史冻结保留。文本还不能冻结。高严重度缺口是 F-001：所谓可验证，目前是一份登记字段和一条正向演示，没有回答是否成立的判定。

建议用户通过 `/govern` 先修订草案并闭合 F-001～F-006，再决定是否确认 D-028。VP-003 的范围澄清按 F-003 单独裁决。本意见不授权改 R1、Root、VP、方法正文或 R4 状态。
