## D-002 · R1 澄清与冻结：方法工作版范围、限额与工具边界

### 触发

R1 的退出条件为：`I-001`（方法工作版适用对象与退出形态、限额与责任）与 `I-003`（配套工具是否引入及其最小交付边界）有确认结论，且结论在 `WRK-002` 主记录与下游 `exchange/WRK-002-world-model-method-and-tools/` 材料中可核对。两项的责任人均为用户。

用户 2026-09-26 就三个门禁问题逐项裁决：范围与退出形态「按建议冻结」、限额与责任「按建议确认」、工具边界「本轮不引入程序化工具，并写清触发条件与再议路径」。

### 决定

1. **适用对象（`I-001`）**：下游世界模型服务——机制层（模型解释「为什么 / 在什么条件下 / 如何相互作用 / 会怎样变化」）、世界级共享状态层（记录「现在是什么」），以及二者结合产生的**裁决结果**。

   覆盖闭环：识别客观裁决需求 → 能力发现 → 缺口归类（缺状态 / 缺组合 / 缺精度 / 缺机制）→ 定义新裁决能力 → 构造最低充分机制模型 → 反补丁与条件敏感性检查 → 模型组合与冲突处理 → 版本与受影响旧裁决管理 → 能力回流创作。

   **不覆盖**下游需求原文 §12 全部十一项：剧情大纲、主题选择、宏观历史演化、叙事窗口、角色选取、BDI 或其他角色决策、角色风险控制、观众信息呈现、自动编剧、完整世界模拟器、固定软件架构。
2. **退出形态（`I-001`）**：一份《世界模型构建方法（工作版）》，纯文本 Markdown / UTF-8 无 BOM / LF，至少含：

   | # | 方法章节 | 对应需求原文 |
   |---|----------|--------------|
   | 1 | 三概念区分（世界模型 / 世界状态 / 裁决结果）与**可操作归属判定谓词** | §4 |
   | 2 | 两类对外服务（能力发现 / 客观裁决）的输入-输出契约，含「不得为满足调用方而伪造精度或确定性」纪律 | §5 |
   | 3 | 定性与定量的统一处理（定量 = 将状态参数代入机制模型后求值） | §6 |
   | 4 | 五条构建原则及其执行检查（机制优先、允许基本前提、允许未定义、禁止结果补丁、模型相互兼容） | §7 |
   | 5 | 现实参考的使用边界（物理 / 生理 / 工程 vs 社会规范 / 组织 / 行为 / 权力 / 声誉 / 群体决策） | §8 |
   | 6 | 新模型最低要求十一项 | §9 |
   | 7 | 缺口判定五步次序 | §10 |
   | 8 | 版本与受影响旧裁决的失效 / 重算声明 | §11 |
   | 9 | 十项指导到方法章节的**可核对映射表** | §13 |

   随交付两个**可操作最小结构**：「**能力缺口判定清单**」（对应 §10）与「**模型条目最小结构**」（对应 §9）。二者属**方法正文的一部分**，不是独立程序化工具。

   响应包须含协议要求的要素：交付版本、适用条件、验证结论与证据、限制、未决事项、后续责任。
3. **限额（`I-001`）**：一条处理主线 `WRK-002`；方法工作版 1 份 + 最小结构 ≤2 份；有界检验 1 次，用例为下游 `I-011` / 本仓 `I-002`（由其最晚需要阶段前选定）。超出即重新澄清；范围外新工作另建主线。
4. **责任（`I-001`）**：需求方、授权人、验收责任人为用户；响应形成、投放与运行记录为方法工程响应负责人；助手的每项代行须逐次授权并逐条标明，代行不构成独立团队共识，也不替代用户本人的价值判断。
5. **工具边界（`I-003`）**：本轮**不引入程序化工具**——不建脚本、linter、链接检查器、生成器、校验器或任何自动化流程。工具的最小交付形态即第 2 项的两个纯文本最小结构。

   **触发条件**：下游在真实使用中确认某类操作重复出现、且重复使用确有价值（需求原文 §9「结构化和工具化只在重复使用确有价值后进行」）后，再另行澄清并按下游 `I-005` 裁决启用。**责任**：触发判断由下游提出；本仓不主动推动工具化。
6. **明确不主张**：方法普遍有效；已关闭下游承载未知 `U-1`～`U-8`；替代下游 canon 裁决。
7. **状态与门禁**：`I-001`、`I-003` 置 `verified`，R1 记完成；`WRK-002` 运行主记录由「已接受」转**「响应中」**（R1 冻结即开始具体响应工作）。`I-002` 在 R4 检验前关闭；`I-004` 在 R4 交付放行前关闭。
8. **`R3` 的处置**：R3（配套工具界定与形成）经复核**无独立形成工作**——其「明确写入本轮不引入工具及其触发条件与责任」分支已由本决定第 5 项给出。该检查点**仍记未完成**，待交付材料随方法工作版一并落定后确认；本轮**不计入** `progress`。
9. **审计模式**：R1 为 `self`。R4 交付前的高影响门禁按 `I-004` 由用户指定 provider 独立审计，不以本次 `self` 顶替，也不得因 provider 不可用而静默降级。

### 为什么

- 需求原文已经把方法应覆盖的操作面写全（§4～§11、§13），因此「适用对象与退出形态」可由原文直接冻结，不需要新增领域判断。
- 把「能力缺口判定清单」与「模型条目最小结构」纳入方法正文，是因为 §10 的五步次序与 §9 的十一项要求若只以散文给出，下游实操时仍须自行发明结构——那正是本轮要消除的缺口。二者不是程序化工具，故不触发下游 `I-005` 的启用门禁。
- 工具按 §9 的时序保留。本轮没有「重复使用确有价值」的证据；若强推工具，会与下游 Charter「不以工具或发布产物为成功条件」冲突，并把未经验证的工具变成事实上的成功条件。
- R1 冻结即开始具体响应，故运行主记录转「响应中」。这不是交付，也不是收件或验收。
- R3 不计入 progress 是保守处理：其退出条件中的「明确写入」应当落到**交付材料**，而交付材料尚未形成；宁可少报，也不把尚未交付的结论记成已完成检查点。

### 未选方案

- **收窄为只交付主文档**：未选。会让 §9 / §10 的可操作性缺口保留，与方法应「可实际运行」的要求不符。
- **扩大为附带端到端示例走查**：未选。示例实质是 R4 有界检验的结果，提前并入交付物会把「方法」与「方法的验证」混为一谈。
- **本轮交付极简程序化工具**：未选。缺重复使用证据，且会新增需下游裁决的交付物与验证成本。
- **把工具形态完全留给下游验收时提出**：未选。会使 R3 / R4 的门禁悬空，无法在交付前判断是否就绪。
- **在 R1 使用独立审计**：未选。R1 为可逆的方案冻结；高影响门禁在 R4，已由 `I-004` 约束。
- **把 R3 记为已完成以体现「无工具」结论**：未选。交付材料尚未形成，先记完成会高报进度（见上「为什么」末条）。
