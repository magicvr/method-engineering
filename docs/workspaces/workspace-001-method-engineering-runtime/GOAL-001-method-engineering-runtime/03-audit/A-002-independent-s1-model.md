## Findings

### F-001 · E-003 将「复用」误报为「无需方法变更」覆盖

| 字段 | 值 |
|------|-----|
| 严重度 | med |
| 建议 | required |
| status | open |
| 影响门禁 | I-001 验证动作；S1 方案冻结 |
| evidence | `02-execution/E-003-s1-paper-walkthrough.md` W-003 与「推演结论」；`01-decision/D-002-runtime-model.md` 不变量 5；VP-001 Intent / 退出判据 3 |
| closure | — |

W-003 场景是「接受后复用成熟方法」，路径为完整主路径。推演结论却写「覆盖……无需方法变更」。D-002 把「复用」与「确认无需方法变更」列为不同响应；不变量 5 还要求「无需方法变更」仍有判断依据和适当验证、且不强制制造方法工件。复用是一种方法响应，不是「确认无需方法变更」。I-001 的收集动作明确要求用有限 walkthrough 检查内部连贯性；当前证据对这条区分是错的，不能当作已走通。

建议补一条纸面路径（例如 W-008）：已接受 → 响应中（记录「现有方法已覆盖、无需变更」的判断依据）→ 验证中（验证该主张，而非新方法工件）→ 已交付 → 已退出；并改正 E-003 结论，把 W-003 只标为复用。

### F-002 · 三层反馈分类未冻结，纸面路径未区分

| 字段 | 值 |
|------|-----|
| 严重度 | med |
| 建议 | required |
| status | open |
| 影响门禁 | I-001；S1 退出中的「明确……反馈」；VP-001.6 |
| evidence | D-002 §3 末句；E-003 W-006；Root `00-meta.md` 成功标准 2；VP-001 Desired Outcome / 退出判据 6；A-001 对照表未列该项 |
| closure | — |

S1 退出条件要求明确反馈语义。VP-001 与 Root 成功标准要求反馈能区分对象问题、方法问题和运行机制问题。D-002 只有「反馈需能路由为……」一句；真正写成规则的是不变量 6 的另一套切分（原承诺内修正 vs 新增/扩大范围 → 待判定）。W-006 把退出后新反馈一律送回待判定，没有三层路由，也没有「何种反馈不构成方法工作授权」。

不变量 6 的授权切分必要，但不能代替层次区分。缺少最小语义时，S2 无法从运行责任反推记录字段，S3 也无法检验 VP-001.6。

建议在修订 D-002 时至少冻结下表，并用一条纸面路径覆盖三种路由（可与 W-006 拆开）：

| 类型 | 最小含义 | 运行后果（建议） |
|------|----------|------------------|
| 对象问题 | 不否定方法本身；问题在对象侧使用、数据或环境 | 不授权方法变更；原承诺内可有界修正使用，或作为新对象需求进入待判定 |
| 方法问题 | 方法选择、内容、适用边界或验证主张需要修订 | 原承诺内有界返回响应中；扩大范围则新待判定 |
| 运行机制问题 | 状态、授权、追踪或责任规则本身有缺陷 | 不得当作方法响应当成功能需求偷偷改机制；进入机制修订/治理路径 |

### F-003 · 「验证失败」与「关键未知」的目标状态未冻结

| 字段 | 值 |
|------|-----|
| 严重度 | med |
| 建议 | required |
| status | open |
| 影响门禁 | I-001 的「转换」；S1 方案冻结 |
| evidence | D-002 §2「验证中」离开条件；不变量 2、3；E-003 W-004；`docs/architecture/principles.md` P-005 实施门禁第 3 点 |
| closure | — |

「验证中」同时写了：通过 → 已交付；失败 → 有界返回响应中；关键未知 → 停止受影响动作。第三条没有目标状态。不变量 2 规定等待不新增主状态；P-005 要求实施中发现关键未知时暂停受影响范围并回流信息登记，而不是自动改写工作授权。

W-004 把「验证失败并出现关键未知」合成一条：验证中 → 停止受影响动作 → 响应中。这把暂停与返工混成同一步，无法核对该需求此时算返工、算等待中的验证，还是算需要重新确认承诺。不变量 3 已要求改边界必须重新确认承诺，但未给出确认期间的状态（已接受 / 待判定 / 仍为验证中）。

建议拆成互斥离开规则后再重跑纸面路径，例如：

1. 验证通过 → 已交付
2. 验证失败且边界/限额不变 → 响应中
3. 验证失败或澄清表明必须改边界/限额 → 停止；重新确认承诺（需写明落在已接受还是待判定）
4. 出现关键未知、尚未形成失败结论 → 保持验证中（等待，不新增状态），停止受影响动作并登记信息项；不得进入已交付，也不得把暂停写成已返回响应中

### F-004 · 纸面 walkthrough 未实例化 D-002 自列的追踪问句

| evidence | D-002 §3「谁提出了什么问题 → … → 为什么结束」；E-003 W-001～W-007 均为一行路径 |
| closure | — |

D-002 要求运行记录至少能回答提出者、接受边界、响应理由、被验证的响应版本与主张、交接对象、反馈、结束原因。E-003 是覆盖矩阵，没有一条虚构需求 ID、责任人、响应版本或验证主张。状态/IDLE 粗核对仍有价值，但责任交接与追踪关系无法按 D-002 自己的问句复验。补 F-001～F-003 的路径时，应用同一条虚构需求把该问句走一遍。

### F-005 · 「声明 / 假设 / 适用条件 / 已验证结论」仅点名

| 字段 | 值 |
|------|-----|
| 严重度 | med |
| 建议 | recommended |
| status | open |
| 影响门禁 | VP-001.5 的 S1 语义最低要求；字段承载仍属 S2 |
| evidence | D-002 §3 追踪段；VP-001 退出判据 5；E-003 无对应场景 |
| closure | — |

S1/S2 边界不允许在 S1 设计完整 Artifact/Evidence Schema，但 VP-001.5 要求运行中能区分这四类内容。D-002 只要求「保持可辨别」，未说明它们在哪些事件产生、验证结论能对哪些主张背书、假设未验证时不得写成已交付成功。S2 若只按名词建字段，会把未冻的语义装进目录。建议在 D-002 追踪要求中各用一句话定义，并用纸面路径表明：验证中通过的是「针对某响应版本的已验证结论」，不是把假设改写为普遍有效。
