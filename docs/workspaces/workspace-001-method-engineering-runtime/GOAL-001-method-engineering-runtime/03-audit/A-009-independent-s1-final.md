## Findings

### F-001 · 「开始条件」相对已接受内容未定义，重确认「尚未具备」分支没有实例

| 字段 | 值 |
|------|-----|
| 严重度 | med |
| 建议 | recommended |
| status | open |
| 影响门禁 | I-001 转换的可演示性；S2 从运行责任反推记录前建议吸收。**不阻断** 本条之后将 I-001 标为 `verified` 或完成 S1 |
| evidence | D-002 v0.4.0 状态表「已接受」离开条件；不变量 3；语义接缝修正第三条；E-003 W-010、W-014；A-008「已接受与响应中是否重叠」行 |
| closure | — |

v0.4.0 把「已接受」与「响应中」拆成授权 vs 已开始工作，主路径 W-014 可重复核对，不构成与不变量 1 的互否。重确认落点也已从 A-006 时的「是否重选响应」改成「是否具备开始响应条件」。

仍未写清的是：**「开始响应工作的必要信息」比「已接受」已经确认的边界、责任人、限额和最小验证方向多了什么。** 已接受的离开条件用两个合取（具备必要信息与授权，并且开始执行）；不变量 3 与 W-010 只用「具备 / 不具备开始条件」在「响应中」与「已接受」之间分流。三种可读法并存：

1. 「尚未具备」= 授权已在、只是还没开始工作（与 W-014 的接缝同向）；
2. 「尚未具备」= 接受之后仍缺一类未点名的启动信息；
3. 若已接受已包含全部启动信息，则「尚未具备 → 已接受」是死分支。

W-010 只点名「尚不具备开始条件 → 已接受」，没有给出缺失项实例；也没有一条「已接受后尚未开始检索、整体非 IDLE、且未形成候选方法」的纸面行。A-008 的 IDLE 核对此前只引用 W-005 / W-006 / W-012 / W-013（已交付等待与退出后反馈），没有覆盖这个新接缝造成的已接受驻留。

这不是两套规则给出相反下一状态（因此不升为 required），而是落点谓语未操作化。S2 若把「开始条件」发明成接受之后的第二套信息门禁，会超出本轮「未新增状态、角色、对象或协议」的声明。

建议 `/govern` 在 D-002 用一句话选定谓语，并让不变量 3、已接受离开条件与 W-010 使用同一套：

- 若驻留只表示尚未开始：写明「原范围重确认后，未开始检索 / 判断 / 形成响应则回到或保持已接受；一旦开始则进入响应中」；
- 若接受与开始之间确有额外必要信息：列出最小类别（仍不要做 schema）。

纸面至少补一行：已接受、尚未开始、不形成候选、因仍有承诺故非 IDLE。验证中行可像已交付行一样转引不变量 3 的三个落点，避免只读状态表的人看不到「验证中 → 已接受」。

### F-002 · 「响应中」发现必须改边界或出现关键未知时，离开条件未写明

| 字段 | 值 |
|------|-----|
| 严重度 | low |
| 建议 | recommended |
| status | open |
| 影响门禁 | S2 反推「响应选择」记录前建议补一句。**不阻断** I-001；不重新打开 A-002 F-003 |
| evidence | D-002 状态表「响应中」离开条件仅「进入验证中 / 有界退出」；不变量 3 标题为「验证相关转换」；E-003 无响应中改边界 / 关键未知行 |
| closure | — |

不变量 4 已允许任一未退出状态有界退出，因此「响应中发现范围不够」并非无下一状态。与验证中 / 已交付已写明的重确认路径不对称：只读「响应中」行的人可能把扩范围当成默认继续检索。建议补一句：响应中若必须改变边界 / 限额，停止受影响动作并有界退出或回到待判定重新接受，不得在响应中直接扩大授权；关键未知则保持响应中等待或按不变量 4 有界退出。可并入 S2 责任反推，不必为此再开 independent 才能标 I-001 `verified`。
