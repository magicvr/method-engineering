# D-002 · S1 需求—响应运行模型与交叉审计路径

## 触发

用户确认按现有范围进入 Root 的 S1「冻结运行模型」，并选择“需求—响应状态模型 + cross 审视”。独立 provider 指定为本地 Grok Build CLI，模型 `grok-4.6`，思考强度 `xhigh`。

本决定承接 VP-001、Root 的 S1 路线图和 I-001；不把当前设计写成已经运行的产品机制，也不把纸面 walkthrough 写成真实 Method Case。

## 决定

### 1. 采用需求—响应状态模型

以一条需求及其处理承诺为追踪主线，用少量状态控制工作授权；接收、澄清、验证、交付和反馈是围绕状态发生的活动或事件，不各自建立第二套状态源。

只冻结三个最小概念：

- **需求信号**：来自可追踪下游实践的问题描述；信息可以不足，提交者不必预先证明方法缺口。
- **已接受需求**：责任方已确认问题边界、处理限额和最小验证方向，并授权一次有界处理；接受不等于承诺新建方法或保证成功。
- **方法响应**：针对该需求选定的处理及其结论，可为选择、复用、裁剪、组合、修改、新建，或确认无需方法变更。

### 2. 冻结最小状态与转换

| 状态 | 含义 | 主要离开条件 |
|------|------|-------------|
| **待判定** | 已收到信号，尚未接受处理承诺 | 信息足够且获得接受授权，进入「已接受」；或明确不受理/撤回，记录退出结果 |
| **已接受** | 已确认需求边界、责任人、处理限额和最小验证方向，并授权一次有界的方法工程处理；此时不要求已经确定具体响应 | 已具备开始响应工作的必要信息和授权条件，开始执行响应工作并进入「响应中」 |
| **响应中** | 已在接受的边界和限额内开始检索、判断、选择、复用、裁剪、组合、修改或形成最小合适的方法响应 | 形成可核对的候选响应和验证安排，进入「验证中」；必要时有界退出 |
| **验证中** | 核对候选响应是否满足本次约定 | 验证通过进入「已交付」；失败且边界/限额不变时返回「响应中」；需要改边界/限额时停止并重新确认承诺；关键未知未形成失败结论时保持「验证中」并登记等待 |
| **已交付** | 已完成交接，仍可能有约定的反馈或收尾义务 | 反馈先分类：原承诺内的对象问题做有界对象侧修正；原边界/限额内的方法问题进入「响应中」；需改变边界/限额时保持「已交付」作为旧交付记录，停止受影响后续动作并登记重确认，确认后按不变量 3 落点；运行机制问题走机制修订路径；满足收尾条件后进入「已退出」 |
| **已退出** | 本轮没有剩余处理承诺 | 后续反馈或新问题保留旧记录为「已退出」，作为新信号进入新的「待判定」；获得新接受授权后才可进入「已接受」，不自动恢复旧承诺 |

主路径为：

`待判定 → 已接受 → 响应中 → 验证中 → 已交付 → 已退出`

「已接受」表示处理承诺已经建立，不要求具体采用哪一种响应已经选定；「响应中」从实际开始检索、判断或形成响应工作时开始。接受授权本身不等于已经开始响应工作。

运行不变量：

1. 接受前允许澄清，但未经接受不得形成候选方法、开展实验或启动无边界研究。
2. 等待不新增主状态；等待中的已接受需求仍是未履行承诺，不能算作 IDLE。
3. 验证相关转换必须区分三种情况：验证失败且边界/限额不变时返回「响应中」；对仍处于验证中的需求，验证失败或澄清表明必须改变边界/限额时停止受影响动作，重确认期间保持「验证中」并登记等待，确认仍在原范围内且已具备开始响应工作的必要信息和授权条件时进入「响应中」，确认仍在原范围内但开始条件尚未具备时保持「已接受」，范围扩大则回到「待判定」；出现关键未知但尚未形成失败结论时保持「验证中」，登记信息项并等待，不进入「已交付」或自动改写为「响应中」。对已交付期间收到且要求改变边界/限额的反馈，保持「已交付」作为旧交付记录，停止受影响后续动作并登记重确认，确认后再按上述落点处理。
4. 任一未退出状态都可以有界退出，但必须记录授权依据、原因、已有产物、未完成内容和后续责任；退出不等于成功。
5. 「无需方法变更」仍需判断依据和适当验证，可快速经过响应、验证、交付，不强制制造方法工件。
6. 反馈不会自行授权新工作；反馈先按对象问题、方法问题或运行机制问题分类，再按下表处理：

   | 反馈类型 | 最小含义 | 运行后果 |
   |----------|----------|----------|
   | **对象问题** | 问题在对象侧使用、数据或环境，不否定方法本身 | 不授权方法变更；可在原承诺内有界修正对象侧使用，或作为新的对象需求进入「待判定」 |
   | **方法问题** | 方法选择、内容、适用边界或验证主张需要修订 | 若反馈发生在「已交付」且仍在原边界/限额内，回到「响应中」；若需改变边界/限额，保持「已交付」作为旧交付状态，停止受影响后续动作并登记重确认，再按不变量 3 落点；若反馈发生在「已退出」之后，不直接恢复旧承诺，而以新信号进入「待判定」 |
   | **运行机制问题** | 状态、授权、追踪或责任规则本身有缺陷 | 不把它偷偷转成方法响应；进入机制修订/治理路径，相关方法工作保持暂停或按当前承诺有界退出 |

   只有分类后的明确授权才会启动相应工作。已交付期间仍受原承诺约束，允许按上表进入原承诺内的响应或验证；已退出后旧记录不再承载新授权，分类结果须挂到新信号并从「待判定」重新开始。
7. **IDLE** 定义为不存在处于「已接受、响应中、验证中、已交付」的需求；它允许接收信号和做准入澄清，但不授权未经接受的方法构建。

### 3. 责任边界与追踪要求

| 责任位置 | 责任 | 权限边界 |
|----------|------|----------|
| 需求方 / 授权人 | 确认真实背景、需求边界、接受与撤回、范围变更和有界退出 | 不把需求愿望当作方法有效性证据 |
| Method Engineering 响应负责人 | 澄清、成熟方法检索与适配判断、最小响应选择、组织验证、交付和记录 | 不自行扩张需求或接受未授权的残余风险 |
| 使用者 / 验证者 | 按约定条件使用或检查响应，提供观察与反馈 | 结论限于实际验证条件，不推为普遍有效 |
| 既有治理责任人 / 审计者 | 按现行治理规则处理目标推进、信息门禁和 findings | 运行状态不代替 Goal 状态或审计放行 |

这些是责任位置，不要求四个独立人员；同一人可以兼任，但响应作者不得冒充独立审计者。运行记录至少应能回答：

> 谁提出了什么问题 → 谁接受了什么边界 → 为什么选择此响应 → 验证了哪个响应版本、哪些主张 → 交给谁 → 得到什么反馈 → 为什么结束或再次处理。

转换记录需保留前后状态、触发原因、责任人和依据；验证结论需指向具体响应版本、条件和证据。运行记录还需区分：

- **方法声明**：关于某个响应或方法“主张做什么/能解决什么”的命题，本身不是验证结论。
- **假设**：处理或验证依赖但尚未由证据确认的前提；未确认时不得写成已验证事实或成功交付。
- **适用条件**：响应可以被使用或验证的对象、环境、输入或边界条件。
- **已验证结论**：在明确响应版本、适用条件和验证范围内由证据支持的结论，不自动推广为普遍有效。

反馈需能按上表路由为对象问题、方法问题或运行机制问题。单条运行记录至少应能实例化「谁提出了什么问题 → 谁接受了什么边界 → 为什么选择此响应 → 验证了哪个响应版本、哪些主张 → 交给谁 → 得到什么反馈 → 为什么结束或再次处理」这条追踪问句。

### 4. S1 / S2 边界与 I-001

S1 只冻结语义、转换条件、责任和追踪关系。S2 再根据这些责任决定最小记录对象、状态承载位置、编号、目录、模板和交接字段；不在 S1 预先设计完整 Artifact Schema、Evidence Schema、方法知识库或自动化平台。

I-001 在语义确定、有限纸面 walkthrough 有证据、self 审视和指定 independent 审视均完成且无未闭合 required finding 后，才可标为 `verified`。本决定本身不关闭 I-001。

S1 的纸面证据必须至少包含一条「确认无需方法变更」路径、一条三层反馈分类路径和一条区分验证失败/改边界重确认/关键未知等待的路径；其中至少一条使用虚构但可追踪的需求 ID、责任位置、响应版本、验证主张和结束原因，且明确标注不是真实 Case。

### 5. 审计路径

本阶段采用 `cross`：

- 由当前治理会话完成一条 `source: self` 的 S1 阶段审视；
- 由用户指定的本地 Grok Build CLI 运行 `source: independent` 的 Goal audit，模型 `grok-4.6`、思考强度 `xhigh`；
- provider 不可用、失败或无可核对输出时，cross 门禁保持未满足，不得由其他模型代替 Grok 意见。

## 为什么

VP-001 的关键问题不是固定流程是否走完，而是何时允许开始、何时继续、何时停止，以及反馈何时构成新一轮授权。线性阶段模型易把活动完成误作状态通过，且需要额外解释等待、交付后的义务和反馈重入。

需求—响应模型直接承载这些授权边界；由 IDLE 推导全局空闲状态，避免新增独立状态源；把验证、交付和反馈保留为活动/事件，避免在尚无真实 Case 时过早冻结复杂对象。

## 未选方案

### 线性阶段模型

可表达“接收→澄清→响应→验证→交付→反馈→退出”，也较容易人工理解；但等待是否仍有承诺、交付后何时结束、反馈是否重启工作都需要额外规则，容易掩盖授权边界，因此不作为主模型。

### 预先建立完整对象与字段体系

会把假设的未来 Case、方法资产和证据结构提前写死，超出 VP-001 的最小范围；延后到 S2，且每个保留对象必须能指回本决定冻结的运行责任。

## 影响与复审条件

- Root 仍为 `active`，不创建子目标，不改变 S1→S2→S3 路线图。
- I-001 保持 `open`，I-002 保持 `open`。
- 任何需要自动接受、无限期等待反馈、并行调度或改变需求边界的设计，都需在后续决定中重新确认授权与责任规则。
- 如果纸面 walkthrough 或任一审计发现状态、授权、退出或追踪语义矛盾，应先修订本决定并重新审视，再推进 S2。

## S1 语义接缝修正（2026-09-18）

- 将「已接受」统一为已建立一次有边界处理授权的状态；它不要求具体响应已经选定。
- 将「响应中」统一为已开始在该授权范围内进行检索、判断、选择、复用、裁剪、组合、修改或形成响应的状态。
- 将重确认后的落点改为：原范围内且已具备开始响应条件则进入「响应中」；原范围内但开始条件仍未具备则保持「已接受」；范围扩大则回到「待判定」。未新增状态、角色、对象或协议。
