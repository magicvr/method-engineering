# E-003 · S1 有限纸面 walkthrough

## 已发生事实

依据 D-002 的状态、转换和不变量，对运行模型做了有限纸面推演。该推演只验证模型内部语义，不是真实下游需求、真实 Method Case 或具体方法有效性证据。

| 场景 | 推演路径 | 结果 |
|------|----------|------|
| W-001 无需求，仅有待澄清信号 | 无已接受需求；允许准入澄清，不进入响应中 | 保持 IDLE，未授权方法构建 |
| W-002 信号不足、超出边界或被撤回 | 待判定 → 记录澄清/不受理/撤回 → 已退出 | 不伪造接受，退出原因和后续责任可记录 |
| W-003 接受后复用成熟方法 | 待判定 → 已接受（边界、责任、限额和验证方向已授权，尚未选定响应）→ 响应中（开始检索并选择复用）→ 验证中 → 已交付 → 已退出 | 记录复用的既有方法版本和适用条件；不把复用写成「无需方法变更」 |
| W-004 验证失败且边界/限额不变 | 验证中 → 响应中 | 失败结论可核对，允许原承诺内有界返工，不进入已交付 |
| W-005 已交付但尚无反馈 | 已交付保持当前承诺，按约定等待或有界退出 | 沉默不被解释为成功；等待中的承诺不算 IDLE |
| W-006 退出后出现新反馈 | 已退出旧记录保持不变 → 新反馈作为新信号进入待判定 → 分类后重新接受或转机制修订 | 保留旧结论，不自动恢复旧承诺；反馈不自动授权 |
| W-007 多条需求并存 | 一条已退出，另一条仍处于验证中 | 整体不误报 IDLE；以仍未退出的承诺为准 |
| W-008 确认无需方法变更 | 待判定 → 已接受（授权一次有界判断，尚未确定结论）→ 响应中（开始检索并记录“现有方法已覆盖”的判断依据）→ 验证中（验证该判断）→ 已交付 → 已退出 | 不制造方法工件；验证的是无需变更主张，不是复用路径 |
| W-009 三层反馈分类 | 已交付或已退出记录收到反馈 → 先区分对象问题 / 方法问题 / 运行机制问题；已退出时另建待判定信号 | 对象问题不授权方法变更；已交付期间的原承诺内方法问题回到响应中；已退出后的新方法问题必须重新接受；机制问题进入机制修订路径 |
| W-010 验证失败、改边界和关键未知分离 | 验证失败且边界不变 → 响应中；需改边界/限额 → 停止受影响动作，验证中保持等待并重确认，原范围且具备开始响应条件 → 响应中，原范围但尚不具备开始条件 → 已接受，扩大 → 待判定；关键未知未成失败结论 → 保持验证中并登记等待 | 三种情况不互相伪装；任何一种都不得直接进入已交付 |
| W-011 可追踪纸面需求 | 虚构 `REQ-PAPER-001`：需求方/授权人确认边界；响应负责人选择 `R-001 v0.1`；验证者核对声明、假设和适用条件；交付后记录反馈与结束原因 | 追踪问句可逐项回答；明确为机制推演，不是真实 Case |
| W-012 已交付期间收到方法反馈 | 原范围：已交付 → 方法问题 → 响应中 → 验证中；需改边界：已交付保持为旧交付状态 → 停止受影响后续动作并登记重确认 → 按不变量 3 落到已接受/响应中或待判定 | 原承诺尚未退出时可继续处理；改边界期间主状态单点保持已交付，不得把反馈当作新授权或跳过验证 |
| W-013 已退出后收到方法反馈 | 已退出旧记录保持已退出 → 新方法问题信号进入待判定 → 接受后已接受 → 响应中 | 不直接回到响应中；新边界和责任必须重新接受 |
| W-014 接受与响应开始的接缝 | 待判定 → 已接受（只建立有边界处理授权）→ 响应中（开始检索/判断/选择 `R-001 v0.1`）→ 验证中 | 已接受不要求已经选定方法响应；响应中才发生具体响应工作 |

另行核对了两条禁止转换：未经接受不得从待判定直接进入响应中；验证未通过不得直接进入已交付。两条均被 D-002 的不变量阻止。

W-014 专门核对本次 S1 接缝：授权人先在「已接受」确认对象、边界、限额和最低验证方向，但不替响应负责人预先选择方法；响应负责人开始检索和判断时才进入「响应中」，随后选择 `R-001 v0.1` 并安排验证。该路径没有新增状态或角色。

W-011 的纸面追踪记录如下（仅为机制推演，不是真实 Case）：

| 追踪项 | `REQ-PAPER-001` 的纸面值 |
|--------|---------------------------|
| 谁提出 / 谁接受 | 模拟使用者 `U-001` 提出；运行责任人 `A-001` 接受“只判断现有方法是否需变更、对象为 `O-001`、环境为 `E-001`、限额为一次纸面验证”的边界 |
| 为什么选择响应 | 响应负责人 `RSP-001` 检索到既有方法覆盖 `O-001/E-001` 的问题类型，选择 `R-001 v0.1`，不把复用等同于无需变更 |
| 方法声明与假设 | 声明：`R-001 v0.1` 能在本次边界内回答是否需要方法变更；假设：输入资料完整且未超出约定对象/环境；假设未被验证前不视为事实 |
| 适用条件与验证结论 | 适用条件 `C-001`：`O-001/E-001`、输入字段完整、只做一次纸面核对；验证者 `V-001` 得出：在 `C-001` 和 `R-001 v0.1` 下，“无需方法变更”成立，结论不推广到其他对象/环境 |
| 交给谁 / 得到什么反馈 | 响应交给模拟使用者 `U-001` 与验证者 `V-001`；已退出后收到“输入字段缺失”的对象问题反馈，反馈提交者为 `U-001`，内容不否定方法结论，旧记录保持已退出并转成新的待判定信号 |
| 为什么结束 / 再次处理 | 本轮因响应版本已验证并完成交接而退出；后续对象反馈不是旧承诺的自动恢复，若提出方法问题则按 W-013 重新接受边界 |

## 推演结论

上述场景覆盖主路径、拒绝/撤回、接受与响应开始的接缝、复用、无需方法变更、验证失败、改边界重确认、关键未知等待、三层反馈路由、已交付期间反馈、已退出后新信号、多需求并存和可追踪责任链。纸面推演未发现修订后状态、授权或 IDLE 定义之间的内部矛盾；本条仅响应当前 S1 接缝，不新增未来机制设计。
