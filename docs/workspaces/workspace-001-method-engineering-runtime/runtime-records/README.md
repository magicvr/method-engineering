# 运行记录最小承载说明

本目录承载已经获得处理承诺的需求运行记录。它支持 Root D-002 v0.4.0 的最小状态、授权、响应、验证、交付、反馈、责任交接和退出语义；不承载 Goal 状态、审计 verdict、具体领域方法知识库或自动化调度。

## 目录约定

每条处理主线使用一个稳定的 `<work-item-id>` 目录：

```text
runtime-records/
├── README.md
└── <work-item-id>/
    ├── record.md
    └── events.md
```

`<work-item-id>` 优先复用需求方已有的稳定需求 ID；没有现成 ID 时，在本工作区内分配 `WRK-NNN-<slug>`。不要把工作区编号嵌入该 ID，也不要使用 `GOAL-*` 作为运行记录 ID。

当前目录只落承载说明，尚无真实需求，因此没有创建示例处理记录或虚构 Method Case。

## 两个记录的职责

### `record.md`

这是处理主线的唯一当前运行状态来源。它至少要让读者能够核对：

- 需求边界、处理限额、授权责任和最低验证方向；
- 当前状态及最近一次状态转换依据；
- 需求方、授权人、Method Engineering 响应负责人、验证者和接收方的责任引用；
- 当前响应版本、验证安排/结论、交付版本、反馈路由和退出结果的引用或最小说明。

「已接受」只记录已经确认的边界、责任、限额和开始响应的条件；具体响应的检索、判断、选择、复用、裁剪、组合、修改或形成发生在「响应中」。

### `events.md`

这是追加式历史追踪记录，不拥有当前状态。每次状态转换、授权、响应选择、验证分支、交接、反馈分类/回流和退出，都追加一条足以核对的事件说明，保留：

- 发生时间与责任人；
- 触发、转换前后状态和判断依据；
- 响应版本、验证条件/证据引用或反馈分类（如适用）；
- 结果、未决事项和下一责任。

即使事件中写有转换前后状态，也只能作为历史证据；当前状态必须读取 `record.md`，不得从事件末条推导或维护第二套状态。

## 最小运行流程

1. 需求进入时创建处理主线，先记录为「待判定」；未获得接受前，不启动候选方法、实验或无界研究。
2. 需求方/授权责任确认边界、限额、责任和最低验证方向后，更新 `record.md` 为「已接受」，并在 `events.md` 记录授权依据；此时不要求已经选定具体响应。
3. 开始具体响应工作时更新为「响应中」，记录响应责任、响应版本和选择/形成理由。
4. 形成可核对的候选响应与验证安排后更新为「验证中」。验证事件必须区分：通过；失败但原边界/限额不变；需要重新确认边界/限额；关键未知尚不能形成失败结论而等待信息。
5. 通过后更新为「已交付」，记录交付版本、接收方、适用条件和未决责任。反馈只先分类为对象问题、方法问题或运行机制问题，再记录处理路由；不会自动产生新的方法工作或恢复旧授权。
6. 本轮承诺结束时记录退出原因和结果，更新为「已退出」。退出不等同成功；边界变化或退出后新信号必须重新进入判定与授权。

## 治理边界

- 本目录的运行状态不替代目标的 `status`、`progress`、信息门禁或审计台账。
- `record.md` 与 `events.md` 只记录本条处理主线；Goal 关系仍由工作区根下的目标五件套和 `goal-tree.md` 维护。
- 方法声明、假设、适用条件和已验证结论必须可区分；本说明不定义完整字段 Schema。
- 如需引用外部响应材料或验证证据，使用稳定路径/版本引用即可；不要因引用而新增强制对象或自动化流程。
