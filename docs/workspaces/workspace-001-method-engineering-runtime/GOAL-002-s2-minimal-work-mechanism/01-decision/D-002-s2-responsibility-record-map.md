# D-002 · S2 运行责任→最小记录需求映射

## 触发

P1 需要把 Root D-002 v0.4.0 已冻结的运行责任、状态转换、授权边界、反馈路由和追踪问句，转换为可落盘的最小记录需求。此记录只完成责任映射，不冻结最终对象名称、字段 Schema、目录实现或自动化。

## 决定

接受下表作为 S2 P1 的记录需求基线。表中“记录/承载需求”是 P2 反推最小工作对象与承载方案的输入；同一条处理主线可以承载多个事件或引用，但 P2 必须保持单一运行状态来源。

## 责任→记录/承载需求

| D-002 运行责任或边界 | 最小记录/承载需求 | 至少需要能够核对的内容 | P2 尚需决定 |
|---|---|---|---|
| 需求进入与「待判定→已接受」 | 一条可追踪的处理主线记录，以及接受/授权事件 | 需求 ID、提出方、授权责任、初始边界、处理限额、最低验证方向、接受依据与状态转换 | 处理主线的对象形态、承载文件与编号方式 |
| 「已接受→响应中」的开始条件 | 处理主线上的响应开始记录或转换记录 | 已有授权边界、响应责任人、开始依据；不要求在已接受阶段预先选定具体响应 | 转换记录是否与生命周期台账同载，以及最小引用形式 |
| 响应检索、判断、选择、复用、裁剪、组合、修改或形成 | 可版本化的响应记录/引用 | 采用的响应版本、选择或形成理由、范围内的处理动作与责任归属 | Method Response 的最小对象边界；不在 P1 展开字段 |
| 方法声明、假设、适用条件与已验证结论的区分 | 响应与验证记录之间的可区分引用 | 四类内容不混写；结论能指向响应版本、适用条件和验证依据 | 是否由同一记录中的不同段落承载，及引用约定 |
| 「响应中→验证中」与验证分支 | 与响应版本绑定的验证事件/记录，以及证据引用 | 验证条件、验证者、证据位置、结论；能区分通过、失败但边界不变、需重新确认、关键未知等待 | 验证记录的最小对象与证据引用承载；不设计 Evidence Schema |
| 「验证中→已交付」与责任交接 | 交付/交接事件或记录 | 交付的响应版本、接收方、适用条件、未决事项和后续责任 | 交付是否作为处理主线事件、独立记录或两者的引用关系 |
| 反馈三分类与路由 | 关联处理主线的反馈事件 | 反馈对象为对象问题、方法问题或运行机制问题；分类依据、处理路由和是否需要重新授权 | 分类与路由的最小承载位置；不得自动授权新的方法工作 |
| 「已交付→响应中/待判定」及退出 | 反馈回流或退出事件 | 原边界内的方法问题回到响应中；边界变化登记重新确认；退出信号形成新待判定；结束原因不等同成功 | 回流与退出事件的具体记录结构和目录承载 |
| 追踪问句与责任交接 | 处理主线内的责任引用和事件链 | 谁提出什么、谁接受什么边界、为何选择此响应、验证哪个版本/主张、交给谁、得到什么反馈、为何结束或再次处理 | 引用粒度与是否需要单独交接记录；不得复制出第二套状态源 |
| 治理边界 | 运行记录与 Goal/Audit 台账的明确分界 | 运行状态只说明本次处理位置；Goal 状态、信息门禁和审计 verdict 仍以治理台账为准 | 文档互链和目录位置，不把运行记录作为 Goal 或审计状态来源 |

## P1 结论

- D-002 的入口、接受、响应、验证、交付、反馈、退出、责任交接和追踪责任均已有最小记录需求，不需要新增状态、角色或对象。
- 「已接受」只记录授权边界和开始工作的条件；具体响应的检索、选择或形成属于「响应中」的记录范围，保持 D-002 的状态语义不重叠。
- 运行状态应由处理主线的一个生命周期承载统一维护；其他记录只能引用或说明该状态，不能形成第二套状态源。
- P1 不冻结最终对象集合、字段、文件编号、目录或流程模板；这些进入 P2 的最小对象与承载方案。

## 后继与信息门禁

本映射作为 `I-201` 的 P1 收集证据。`I-201` 仍处于 `collecting`，因为对象边界、承载位置和 P2 方案尚未冻结；Root `I-002` 继续保持 `open`。
