# D-003 · P2 最小工作对象与承载方案（原方案）

> 本决定的对象边界、`record.md` / `events.md` 职责和单一运行状态原则继续有效；仅其“承载于当前工作区根”的位置决定已由 D-004 修正并取代。

## 触发

P1 已完成 D-002 运行责任→记录需求映射，且用户选择 A 方案：每个需求使用一个处理主记录目录，其中包含一个生命周期主记录和一个追加式事件追踪记录。P2 需要把该选择冻结为可落盘的最小对象、状态承载、目录和流程文档边界。

## 决定

S2 采用两个最小工作记录对象，加一个不承载状态的使用说明文档：

1. **处理主记录（`record.md`）**：每个需求一份，是本次处理的唯一当前运行状态来源。它承载需求边界、授权限额、责任引用、当前状态、当前响应版本引用、验证安排/结论引用、交付/反馈/退出结果的最小可核对信息。
2. **事件追踪记录（`events.md`）**：与处理主记录同目录的一份追加式历史记录，承载状态转换、授权、响应选择依据、验证分支、交接、反馈分类与回流、退出原因等时间线证据。它只保留历史追踪，不是当前状态来源。
3. **使用说明（`README.md`）**：说明创建、更新、追加事件、责任交接、验证分支、反馈路由和退出的最小操作；它不是工作对象，也不保存某一需求的状态。

## 目录与编号承载

P3 落盘时使用以下最小结构，位于当前工作区根，不放入某个 `GOAL-*` 目录，也不改变目标树层级：

```text
docs/workspaces/workspace-001-method-engineering-runtime/
└── runtime-records/
    ├── README.md
    └── <work-item-id>/
        ├── record.md
        └── events.md
```

- `<work-item-id>` 优先复用需求方已有的稳定需求 ID；没有现成 ID 时，在当前工作区内分配 `WRK-NNN-<slug>` 形式的本地 ID。
- ID 只用于定位一条处理主线，不把工作区编号嵌入 ID，也不把它当作 Goal ID。
- `record.md` 的当前状态是运行状态唯一权威；`events.md` 可以记录转换前后状态以支持追踪，但不得据此另建当前状态。
- Goal status、progress、信息门禁和 Audit verdict 继续只由工作区目标台账承载；`runtime-records/` 不得替代治理台账。

## 最小对象边界

不为 Method Response、Evidence、反馈类型或每个状态另建强制对象。响应版本、方法声明/假设/适用条件/已验证结论、验证条件与证据引用、反馈三分类和交接信息，先以处理主记录中的最小段落/引用与事件追踪记录承载；只有实际存在的外部材料才需要被链接。P3 不因此设计完整字段 Schema。

这保持以下单一来源关系：

```text
record.md  ──唯一当前运行状态
    └── events.md  ──追加式历史证据，不反向拥有状态

Goal / Audit 台账  ──治理状态与门禁，不由 runtime-records 复制
```

## 生命周期与责任边界

- 新建处理主记录时处于「待判定」；只有接受事件记录了边界、限额、责任和最低验证方向后，才进入「已接受」。
- 从「已接受」开始具体检索、判断、选择、复用、裁剪、组合、修改或形成响应时，主记录进入「响应中」；响应版本和选择依据同时留下引用/事件。
- 进入「验证中」后，事件追踪记录区分通过、失败但边界不变、需要重新确认边界/限额、关键未知等待四个运行结果；验证结论绑定响应版本和条件。
- 「已交付」记录交付版本、接收方、适用条件和未决责任；反馈事件只按对象问题、方法问题、运行机制问题分类并记录路由，不自动恢复旧授权。
- 退出事件记录结束原因、结果和后续触发；退出不等同于成功，边界变化必须重新进入授权判断。

## 未选方案与取舍

- 未选“每个需求单一大文件”：结构最少，但当前状态、历史事件和交接证据容易混在一起，后续追踪和追加边界不清。
- 未选“按状态拆分多个阶段文件”：阅读直观，但会形成多个可能承载当前状态的位置，增加状态漂移风险。
- A 方案多一个事件文件，但把当前状态与历史追踪分开，能够满足 D-002 的追踪问句，同时保持最小对象数量和单一状态来源。

## 原方案的 P2 退出条件

对象集合、记录边界、当前状态唯一承载和必要流程说明的方案已形成。原方案曾将目录放在工作区根；该位置不再作为当前承载依据，后续以 D-004 为准。
