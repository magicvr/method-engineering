# VP-001 · 建立需求驱动的方法工程最小运行机制

## Problem

现行 Charter 已确立真实问题优先、成熟方法优先、证据驱动和可修正的方向，但仓库尚未定义一套正式运行机制，把下游实践暴露的方法问题转化为有边界、可追踪、可验证的方法工程工作。

如果先从目录、文件或完整流程出发，Method Engineering 容易偏离为主动扩张的方法知识库，或提前设计一套并不由真实需求推出的完备方法论体系。

## Intent

建立 Method Engineering 作为需求驱动的方法工程能力的最小正式运行机制：真实下游实践出现方法需求时，能够接收并界定需求，选择最小合适的方法响应，安排有界验证与交付，接收反馈并触发后续判断；在不存在已接受需求时，机制保持 IDLE，不主动启动新的方法构建工作。

“方法响应”不限于新建方法，也包括选择、复用、裁剪、组合、修改，以及确认无需方法变更。

## Desired Outcome

VP-001 完成后，即使尚未发生第一个真实方法需求，Method Engineering 也已经处于可正式运行的状态：

- 无已接受需求时保持 IDLE；
- 真实需求出现时，可以从需求信号推进到响应、验证、交付、反馈或有界退出；
- 需求来源不要求是 Git 仓库或固定接口，而是可追踪的真实下游实践；
- 方法缺口可以在处理过程中判断，不要求下游提交时预先证明；
- 反馈能够区分对象问题、方法问题和运行机制问题；
- 运行机制本身可复核、可修正，但不声称任何具体方法已被证明普遍有效。

## Scope

本 VP 覆盖建立上述运行所必需的最小边界：

1. 什么样的下游实践信号可以成为待处理的方法需求，以及信息不足时如何澄清而不提前启动方法构建。
2. 需求进入、接受、响应选择、验证、交付、反馈和退出之间的基本语义、责任交接和可追踪关系。
3. 下游需求方、方法使用者/验证者与 Method Engineering 之间的最小责任边界。
4. 复用优先，以及选择、复用、裁剪、组合、修改、新建或确认无需方法变更等响应路径。
5. 方法声明、假设、适用条件和已验证结论在运行中能够被承载和区分的最低要求；不预先设计完备的 Method Artifact Schema、Evidence Schema 或方法知识模型。
6. 下游反馈如何重新进入方法判断，并区分对象问题、方法问题和运行机制问题。
7. 在运行模型明确后，从运行责任反推出最小工作对象、状态、仓库结构和流程文档；不为假设中的未来 Case 预先扩展机制。

## Non-goals

本 VP 不包含：

- 本 VP 的完成不要求交付具体领域方法或解决某个具体下游问题；这不禁止正式运行机制在收到真实需求后选择新建方法作为一种响应；
- 把首个真实 Method Case 作为本 VP 完成的前置条件；真实需求若在过程中出现，可以按机制处理，但不因其出现而扩大本 VP 边界；
- 证明具体方法的领域效果、普遍有效性或永久正确性；
- 预先建立完备的方法论、元方法大全、方法分类学、知识库或所有未来 Case 的复杂协议；
- 设计完整、通用或长期稳定的 Method Artifact Schema、Evidence Schema 或方法知识模型；
- 在没有已接受需求时主动开展新的方法构建或无边界研究；
- 建设自动化平台、Web UI、跨仓库请求协议或其他消费适配器；
- 替代现有 Charter、VP、工作区和 Goal 治理，或在愿景层建立第二套执行状态源。

以上 Non-goals 约束的是 VP-001 的完成范围，不是未来运行机制处理真实需求时的响应能力。机制仍可根据需求选择、复用、裁剪、组合、修改、新建，或确认无需方法变更。

## 与 Charter 的对齐边界

VP-001 的完成或将其标为 `closed`，只证明需求驱动的方法工程最小运行机制满足本 VP 的方向级退出判据；它不表示 Charter 的方向级成功边界已经满足，也不收缩 Charter 对真实问题、真实 Case 反馈和明确适用边界的要求。bounded walkthrough 仅验证运行机制自身的内部连贯性，不是真实 Case，也不是具体方法有效性的证据。

## 方向级退出判据

在同时满足下列方向时，本 VP 可以进入有界关门路径；具体证据应由后续工作区承载：

1. 运行机制能够明确表达没有已接受需求时的 IDLE 状态，并且不会从 IDLE 自行授权新的方法构建工作。
2. 参与者能够接收一个来自真实下游实践的方法需求信号；提交者无需预先证明方法缺口，但机制能够判断所需澄清和下一步边界。
3. 机制能够在不新增假设性结构的情况下选择或记录最小合适响应，包括复用既有方法、裁剪/组合/修改、新建，或确认无需方法变更。
4. 从需求进入到响应、验证、交付、反馈和有界退出的责任、交接和追踪关系连贯且无内部矛盾。
5. 运行机制能够承载并区分方法声明、假设、适用条件和已验证结论，但不以此宣称已建立完整方法或证据模型。
6. 下游反馈能够被路由为对象问题、方法问题或运行机制问题；只有经过判断后才进入相应的修订或新需求路径。
7. 一次明确标注为机制验证的 bounded walkthrough 能够检验需求进入、状态转换、责任交接、响应选择、验证、交付、反馈和退出的内部连贯性；该 walkthrough 不是真实 Case，也不用于证明具体方法有效。
8. 由上述运行责任反推出的仓库结构和流程文档保持最小充分；每个保留的对象或文件都有运行责任，不产生重复状态源或无主机制。

本 VP 的正式 `closed` 状态仍须满足愿景对齐规则，并链接工作区中的实施与结项证据；本 VP 不以 progress% 或愿景层流水账作为关门依据。
