# VP-002 · 支持首个真实作品完成故事线规划大纲

## Problem

VP-001 已建立需求进入、接受、响应、验证、交付、反馈和退出的最小运行机制，但该机制尚未经过真实下游作品的实际运行。若没有真实作品作为消费者，Method Engineering 容易重新退化为主动规划方法体系；若没有明确的创作终点，“支持作品跑通”又可能无限扩展到整部作品或所有创作阶段。

VP-002 需要让 Method Engineering 第一次作为上游方法工程支持方，服务一个真实作品仓，并在不预先拆解未来方法 Goal 的前提下，支持该作品完成一个有限且可观察的创作阶段。

## Intent

以一个真实作品仓作为 Method Engineering 的首个实际下游，从作品当前真实状态出发，接收作品方在正常创作中提出的、可以仍然粗略的真实需要或问题信号。Method Engineering 主导需求澄清、问题界定、方法/工具研究、设计、构建、内部验证和交付；作品方不需要先完成方法工程化分解或设计方案。随后作品方在正常创作中使用交付物，并反馈实际现象、影响和预期；Method Engineering 负责诊断、修正和再次交付，直到该作品完成一份包含故事线规划、并由作品方接受的有界大纲成果。

如果作品方在真实实践开始前尚不能合理给出该大纲的最低接受条件或完成后的下一创作阶段，VP-002 允许在 D1 内进行一次有界的创作接受边界探索。探索用于从真实推进中形成作品方自己的候选边界、证据和下一阶段判断，不要求作品方凭空承诺未知答案；该探索不构成所有方法需求的统一前置门禁。最终方向级终点仍是作品方接受一份包含故事线规划、足以进入下一创作阶段的大纲。

VP-002 的 Goal 集合不在本规划阶段预先定义。每个已经出现、被接受且具有独立方法工程边界的真实需求，才可以在 VP-002 对应工作区的 Root 下生成直接子目标；需求较大时，仍可在该子目标下继续派生子目标。方法响应可以是选择、复用、裁剪、组合、修改、新建，或确认无需方法变化。

## Desired Outcome

VP-002 完成时：

- 一个真实作品仓已从其当前状态推进到作品方接受的、包含故事线规划的大纲成果；
- 至少一条真实方法需求经过接受、响应、实际使用和反馈闭环；
- 方法响应确实支持了作品继续推进，而不只是形成上游文档交付；
- 作品方完成了对大纲成果的评阅以及影响本次边界的反馈处置；
- 本次实践的证据能够区分作品问题、方法问题和运行机制问题；
- 所有结论均限定在本作品、本大纲阶段和本次实际条件内，不外推为完整创作方法体系或普遍有效性证明。

## Scope

本 VP 覆盖：

1. 确认首个真实作品仓、作品当前状态、协作责任和本次有界创作实践的范围；若具体创作接受条件或下一阶段尚未知，在 D1 内开展有界定义探索。
2. 将本次有界创作实践的终点定义为：作品方接受一份包含故事线规划、足以进入其下一创作阶段的大纲成果。
3. 在作品真实推进过程中接收可以仍然粗略的实际需要或问题信号，由 Method Engineering 主导澄清和判断是否形成有界方法需求；不要求作品方先完成方法工程化分解。
4. 通过 VP-001 运行机制处理需求；运行记录承载需求的接受、响应、内部验证、交付、正常使用、反馈和退出，Goal 承载具有独立方法工程边界的治理、验收和审计。
5. 由 Method Engineering 负责方法/工具的研究、设计、构建、内部验证和交付；作品仓在正常创作中使用，反馈实际现象、影响和预期，Method Engineering 负责诊断和迭代。
6. 只积累由真实需求触发的响应、经验及其适用条件；不因 VP 的存在预先建立未来创作方法清单。
7. 在大纲成果达到作品方接受点后，对本次支持波次进行有界关门。

## Non-goals

本 VP 不包含：

- 预先建立完整剧情推演方法或完整创作方法体系；
- 为未来可能出现的创作问题预先创建 Goal；
- 完成首个作品的详细创作、整部作品或全部创作阶段；
- 让作品仓适配 Method Engineering 预先设计的完整创作流程；
- 要求作品方在缺乏实践依据时预先虚构最低接受条件或下一创作阶段；探索形成候选不等于作品验收通过；
- 要求作品方承担方法需求的工程化分解、候选方法设计、方法验收方案、根因诊断、候选比较或工程证据整理；
- 把 D1 创作接受边界探索设为所有局部方法需求响应的统一前置门禁；
- 要求每个需求信号、反馈事件或运行记录都单独创建 Goal；
- 证明任何方法在其他作品、其他阶段或一般条件下普遍有效；
- 把作品方的创作 Goal、Method Engineering 的 runtime work item 和 Goal 状态合并为同一套状态源；
- 将大纲完成后的详细创作需求自动并入 VP-002。

## 有界创作实践定义

本 VP 的有界创作实践是：作品仓从当前真实状态出发，围绕一个事先确认的范围推进，形成一份包含故事线规划的大纲，并由作品方按其自身最低接受条件完成评阅和反馈处置。

有界性至少由以下条件共同确定：

- 起点：作品仓、当前版本和当前创作状态明确；
- 对象：本次大纲覆盖和排除的内容明确；
- 终点：大纲达到作品方认为可以进入下一创作阶段的接受点；
- 支持：至少一条真实、已接受的方法需求具有“响应—实际使用—作品推进—反馈”的可追踪证据；
- 扩张控制：超出本次大纲范围、终点或投入限额的需求不得自动并入，须重新判断并可形成后续有界意图。

大纲完成不表示后续详细创作已经完成；后续详细创作即使继续由 Method Engineering 支持，也不自动属于本 VP。

## D1 创作边界探索与局部方法需求响应

当作品方无法在实践开始前合理确定本作品的最低接受条件或完成后的下一创作阶段时，允许在 D1 内进行一次有界探索。探索的唯一目的，是围绕本 VP 已冻结的方向级终点，从作品真实推进中形成作品自己的：

1. 最低接受条件候选及其对应的作品证据；
2. 完成当前大纲后下一创作阶段的候选及进入条件；
3. 由作品方确认的本轮范围、终点和接受判断边界。

该探索不等于验收，不改变“包含故事线规划、足以进入下一创作阶段的大纲”的方向级终点。它服务于作品自身的创作范围、终点和接受判断，不定义方法验收条件，也不统一阻止一个已经足够具体且局部有界的方法需求进入响应。探索受作品方已确认的本次四周总投入上限约束；到期不自动延长，若仍不能形成作品方可接受的边界，则停止并重新判断范围、投入或 VP 对齐。

### 不再设置 D1 前置方法分析

本版本不再设置“D1 内的有限前置方法分析”这一规范性工作类型。v0.3.0 的相关安排曾试图解除未知接受边界造成的死锁，但实际把 Method Engineering 的构建工作和作品方的创作边界探索混在了一起；该安排由本节取代。历史决策、执行条目和工作稿保留，不能被解释为当前仍要求作品方共同构建方法。

如果作品方提出一个仍然粗略的真实需要，Method Engineering 应先主导最小必要澄清。作品方只需提供已有的创作事实、目标、限制以及在使用交付物后观察到的现象、影响和预期；不需要提出候选方法、方法验收方案、根因诊断、候选比较或工程证据整理。

只要一个局部方法需求已经足够具体并且有界，D1 尚未退出不应阻止 D2 的局部响应。Method Engineering 负责该需求的界定、研究、设计、构建、内部验证和交付；作品仓在正常创作中使用，不因使用方法而承担额外的默认实验义务。

如确需比较实验或额外证据收集，应由 Method Engineering 设计目的、步骤、成本和判断办法，并明确征得作品方参与同意；这不是普通使用或反馈的默认要求。作品方反馈的是实际使用现象、影响和预期，不必诊断问题属于作品、方法还是运行机制；分类、根因分析和修正由 Method Engineering 负责。

## 责任边界与运行闭环

| 工作 | 作品仓 / 作品方 | Method Engineering |
|------|------------------|---------------------|
| 需求提出 | 在正常创作中说明想做什么、哪里需要帮助；可以粗略，不必工程化 | 接收信号并决定最小澄清路径 |
| 需求澄清 | 提供必要的创作事实、目标和限制 | 主导提问、问题界定、边界与响应建议 |
| 方法设计与构建 | 提供必要的领域判断，不负责候选设计 | 研究、取舍、设计、构建、内部验证和交付 |
| 正常使用 | 在正常创作中使用，决定是否采用及作品是否满意 | 提供必要支持，避免把额外方法工作变成默认使用义务 |
| 反馈与迭代 | 描述实际现象、影响和预期，不必诊断根因 | 诊断作品/方法/运行问题，修正、验证和再交付 |
| 作品验收 | 决定作品范围、成果和大纲是否接受 | 提供支持，不代替创作判断 |

方法的交付检查和内部验证由 Method Engineering 负责提出和执行；作品方对其在真实创作中的实际有用性和作品成果作出使用反馈与创作接受判断。两者不能互相替代。

## D1/D2/D3 方向级关系

D1 与 D2 不是所有工作都必须严格串行的两道统一门禁。D1 继续探索作品自身的创作接受边界；D2 在出现足够具体且局部有界的真实方法需求后即可启动，必要时与 D1 并行或局部交错。D1 的未决不应阻止局部方法响应，D2 的方法构建也不替代 D1 或作品方对创作终点的判断。

## 与 Charter 的对齐边界

VP-002 的完成或 `closed` 只证明本波次的方向级退出判据已满足，不表示 Charter 的方向级成功边界已经满足，也不收缩 Charter 继续要求的真实问题优先、持续真实 Case 反馈和有界积累。

本 VP 至少一条真实需求的闭环，不等于 Charter 所要求的持续真实 Case 反馈已经完成；作品方接受一份包含故事线规划的大纲，也不等于任何具体方法已被证明普遍有效。后续实践仍须在 Charter 边界内继续接受真实问题和证据驱动的检验。

## Goal 与 runtime work item 的关系

VP-002 只冻结意图和方向级边界，不预先冻结 Goal 树。

- 未接受的需求信号先进入需求澄清和运行记录，不自动创建方法响应 Goal；
- D1 内的接受条件探索仍属于作品自身的有界信息发现；它不定义方法验收，也不成为所有方法响应的统一前置门禁；
- 如果需求澄清本身具有独立的范围、产物、退出判断或审计边界，可以建立一个仅用于澄清的 Goal；该 Goal 不表示方法需求已经接受，也不预授权方法构建、交付或试用；
- 只有在需求澄清形成足够具体、具有独立方法工程交付、判断、验证或审计边界的需求后，才在本 VP 对应工作区 Root 下创建方法响应 Goal；
- 需求较大时，先在该目标内形成高层路线图，再按独立范围、产物或门禁派生下一级子目标；
- 同一需求内的响应迭代和普通反馈不自动产生新的 Goal；
- runtime work item 记录一条需求处理主线的当前运行状态和事件历史，不替代 Goal 的状态、审计或 goal-tree；
- 作品仓自身的创作目标继续由作品仓治理，不成为本仓 Goal 的跨工作区 `parent`。

## 方向级阶段结构

以下仅表达 VP 层的方向先后，不是预先创建的 Goal 清单或可执行路线图：

| 阶段 | 方向 | 退出方向 |
|------|------|----------|
| D1 | 确认首个真实作品和有界大纲实践；必要时在真实推进中探索作品自身的接受条件 | 作品方、作品当前状态、范围、起点、责任和投入限额明确；若具体接受条件或下一阶段已知则直接固定，若未知则完成本 VP 允许的有界定义探索，并由作品方确认创作边界后退出 D1。D1 不定义方法验收，也不统一阻止局部 D2 响应。若探索无法在四周总上限内形成可接受边界，停止并回流 `/vision`，不得扩张「大纲」语义或要求作品适配预设流程 |
| D2 | 在真实作品推进中接收并处理局部方法需求，由 Method Engineering 主导方法工程响应；可与 D1 并行或局部交错 | 至少一条真实需求完成“响应—使用—反馈—处置”闭环；D1 的未决不被伪装成方法构建任务，也不能替代该闭环 |
| D3 | 完成并接受包含故事线规划的大纲 | 作品方接受大纲，范围内承诺已处置，进入 VP 关门核对 |

## 方向级退出判据

在同时满足下列方向时，本 VP 可以进入有界关门路径；证据应由实现工作区和作品仓共同提供：

1. 首个真实作品仓、当前状态、大纲范围、起点、责任和投入限额已经明确；若具体接受条件或下一阶段起初未知，已通过 D1 有界探索形成并由作品方确认。
2. 作品从真实创作状态开始推进，而不是通过纸面 walkthrough、模拟材料或预设案例替代真实运行。
3. 至少一条来自真实作品推进的需求已被接受，并按照 VP-001 机制经过响应、验证、交付和反馈处理。
4. 方法响应已经被作品实际使用，作品推进到可核对的大纲成果。
5. 作品方已评阅并接受包含故事线规划的大纲，影响本次边界的反馈已完成修订或明确处置。
6. 本次大纲范围内的 Goal、runtime work item 和必要信息项均已完成、退出或以明确范围和复核条件记录合法残余；范围外的新需求不构成 VP-002 的未完成项。
7. 关门结论明确限定于本作品、本大纲阶段和本次条件，不表示完整创作方法体系、整部作品完成或方法普遍有效。
